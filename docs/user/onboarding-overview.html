ProjexCloud + Projexlight — Onboarding Overview

How the three portals, the identity model, and the SDK backbone fit together — for every persona and every vertical.

How to use this document. This is the front-door guide to onboarding on ProjexCloud. It explains who logs in where, how one person can hold many roles across many applications, how a customer building multiple applications registers and runs them, and a worked robotics / physical-AI example. Persona-specific guides (Tenant Admin, Tenant Developer, App User, Platform Admin, ProjexCloud Admin) live alongside this file in the same folder.

1 · The three portals

ProjexCloud exposes three purpose-built consoles. They are different surfaces over one platform — not three separate products.

App Admin = Tenant Admin. There is no separate “app admin” door. An app’s administrator is a Tenant Admin whose membership carries the admin role for that app’s tenant — they sign in at /tenant. The Platform Admin console (/console) is operator-only and rejects tenant identities.

2 · The login & identity model — do Workspace and Tenant Admin share a login?

Short answer: yes — the same human, the same credential. A person registers once and gets a single canonical identity. Whether they land in Workspace or Tenant Admin is decided not by a separate account, but by the roles and memberships attached to that one identity. It is single sign-on with role-based surfaces.

ProjexCloud models identity in six layers (architecture §7). Each layer answers a question no other layer can:

LayerEntityAnswersExample
L1Master Person — person_idWho is this human, globally?One row per real person, across every app & tenant
L2App Identity — app_identity_idThis person inside one application(person × app) — profile, preferences, notifications per app
L3Tenant Membership — tenant_membership_idThis identity inside one tenant(app-identity × tenant) — carries tenant-scoped roles
L4Persona — persona_idThe “hat” worn hereAdmin, Developer, Operator, Buyer, Patient, Contractor…
L5Encounter — encounter_idA bounded interactionA visit, order, mission, site visit (optional)
L6Relationship — relationship_idA long-running bondHomeowner–Contractor, Patient–Doctor (optional)

On every request the gateway carries the full tuple in the JWT and the Pool Router uses (tenant_id, app_id) to reach the right database pool. So a single login can resolve to Tenant Admin (because your membership carries the tenant-admin role) and to Workspace (because the same membership also carries a developer/builder role).

Platform Admin is the exception. The /console portal is for ProjexCloud operators, not tenant users. It is a platform-level identity (operator persona), and a tenant identity cannot sign into it. Workspace and Tenant Admin share the tenant identity; Platform Admin does not.

Concretely, registration (POST /api/auth/register) creates exactly one identity.person row, one encrypted email identity.alias, and one password identity.credential. Access to each portal is then granted by adding the right tenant membership + persona/role, never by creating a second login.

3 · Scope hierarchy — Org → App → Tenant → BU

Customers who build multiple applications sit inside a four-level scope hierarchy (architecture §7.1). Understanding it is the key to onboarding more than one app.

ScopeMeaningWho owns itExample
org_idMeta-tenant / reseller / holding companyProjexCloud + reselleracme-robotics-group
app_idAn application surface — its own data model & event namespaceRegistered by Platform Admin (App owner)acme.warehouse-bot, acme.humanoid-ops
tenant_idA customer organization inside an appProvisioned per customeracme-plant-dallas, acme-plant-berlin
bu_idA business unit inside a tenant (optional)Tenant Admindallas-line-3, emea-fleet
The rule for multiple apps. One App = one product surface with its own data model. A company building three products registers three Apps. Each App then has its own tenants (its customers or its internal sites), and each tenant has its own members and BUs. Identities are shared at the person level (L1) but isolated per app at L2/L3 — so a developer on acme.warehouse-bot does not automatically see acme.humanoid-ops data.

3.1 · When the apps belong to different companies

Everything above describes one company registering several Apps. The model also covers the case where the tenants are different companies — one uses another's app, and both publish apps of their own. Nothing new is created at the person layer; only the layers above it are added.

You wantWhat is createdLayer
Tenant B's employee uses Tenant A's apptenant_membership in A + app_identity for A's app_id + a second personaL2, L3, L4
Same human keeps their job at Tenant Bnothing — their existing memberships and personas are untouched—
Tenant A subscribes to Tenant B's appthe mirror of row 1, with the roles reversedL2, L3, L4

The same human is one person_id throughout. identity.alias declares UNIQUE (kind, value_hash), so one email resolves to exactly one person platform-wide: a user who later becomes a provider is necessarily the same person, with no account-linking or identity-migration step, because the split never happened.

Three rules that decide whether this works.
  • Membership is the gate, and it belongs to the provider. Logging in with a tenant_id returns 403 NoMembership unless a membership already exists, so nobody joins a tenant by guessing its id. The provider admits them by creating the membership; the app_identity then mints itself on first login.
  • Never register the same human twice. A second POST /api/auth/register fails on the unique alias. That failure is the constraint working — creating a second person would break MDM convergence and split their audit trail permanently.
  • The password is global. One person has one identity.credential, so a credential collected on one provider's own login page also works at every other provider. If your tenants must be mutually untrusting, host login centrally and hand them a redirect flow.
Known gap — an existing user cannot self-serve into a provider. The data model supports it completely; the provisioning endpoint does not. POST /api/auth/signup-tenant raises PersonExistsError when the email already has an alias, and POST /api/tenants accepts no person_id to bind an owner — so neither call promotes an existing user. Compose it from an authorised caller for now: POST /api/tenants → POST /api/memberships (binding the existing person_id) → POST /api/memberships/{id}/personas → POST /api/applications → mint a key. The worked request bodies for all three cases are in the developer hub under Authentication → “One person, many roles”.

4 · End-to-end onboarding flow (using the three portals)

The canonical path from zero to a running application, and who does each step in which portal:

  1. Register the App — *Platform Admin (/console)* or the ProjexCloud onboarding team creates the App record (tenant.app): the product surface, its data model namespace, role-template catalogue, and module subscriptions. Do this once per application.
  2. Provision the Tenant — *Platform Admin* (or self-serve trial signup) creates the tenant under that App: display_name (company), region, isolation tier (S/P/G), optional brand domain. This writes tenant.tenant and assigns pool placement. The first user is auto-promoted to tenant admin.
  3. Tenant Admin sets up the org — *Tenant Admin (/tenant)*: configure billing, invite members by email, assign personas & roles (Developer, Operator, Viewer…), create Business Units, issue API keys, wire connectors/webhooks, set AI providers and BYOK.
  4. Developers build — *Workspace (/workspace)*: invited developers sign in, discover SDKs, compose a build plan (or use the CLI + MCP), and deploy. Multiple developers collaborate inside the same app/tenant; ReBAC governs who can touch what.
  5. End users use the app — the scaffolded vertical application: ordinary users (Buyer, Patient, Operator, Devotee…) sign in with the same identity system, scoped to their persona, with consent and audit on every read of personal data.

5 · Multiple applications, multiple developers

A customer is rarely one app and one developer. The platform is built for the fan-out:

  • One Org can own many Apps (products). Register each App once via Platform Admin.
  • Each App serves many Tenants — either external customers (if you resell) or your own internal sites/plants/regions.
  • Each Tenant has many members. A member is a person + a tenant_membership + one or more personas/roles. Add developers, operators, and viewers here.
  • Each Tenant can have many Business Units (bu_id) with their own approval chains and P&L — e.g. one BU per plant or per region.
  • Developers collaborate in Workspace; their reach is bounded by ReBAC (sdk-rebac) and ABAC policy (sdk-policy), so isolation holds even with many people across many apps.
Same person, many hats. Because identity is layered, one engineer can be a Developer on App A’s tenant, an Admin on App B’s tenant, and a Viewer somewhere else — all under one login. The persona/role on each tenant membership decides what they see.

7 · Worked example — a humanoid robotics OEM (1000s of robots)

A manufacturer produces thousands of humanoid robots and wants a governed fleet backbone: enroll every robot, ingest sensor telemetry, meter per robot, capture evidence-grade camera data, run fleet analytics, and let operators (and AI agents) act safely — across many plants and customers.

7.1 · How they map to the platform

  • Org = the OEM group. App = acme.humanoid-ops (one product surface). Tenants = one per customer or per plant (e.g. acme-plant-dallas). BUs = production lines or regions.
  • Each robot is enrolled as a device (device_uuid) and given a service persona (a non-human identity) bound to a fleet/site — the same six-layer model, with the robot as an L4 service persona instead of a human.
  • Robots authenticate with per-robot API keys / principal tokens (sdk-api-keys, sdk-principal-token), scoped to exactly what that robot may do.

7.2 · Onboarding steps

  1. *Platform Admin* registers the App acme.humanoid-ops and provisions the OEM tenant(s) at the right isolation tier (Tier G if regulated/sovereign).
  2. *Tenant Admin* sets up BUs per plant, invites operators/engineers as members, issues fleet API keys, configures alert webhooks and AI providers (BYOK if required).
  3. *Developers* (Workspace) compose the robotics SDK stack and deploy the fleet backbone + ops console.
  4. Fleet enrollment: each robot calls device enrollment on first boot → gets device_uuid + attestation + a scoped credential. Bulk-enroll via the device SDK for thousands of units.
  5. Steady state: robots stream telemetry (ingest), emit metered usage per action/sensor-frame (meter), capture attested media (evidence), and operators watch dashboards (analytics) with every command audited.

Why it scales to thousands. The platform adds capacity by adding pools, not sharding (architecture §8). Each tenant pins to one Postgres pool per category (≤ ~5k tenants/pool); the Pool Router resolves (tenant_id, app_id) → pool in < 5 ms via Redis. Robot telemetry rides the metering spine (usage.events.v1 → Kafka → ClickHouse rollups), which is built for high-cardinality per-device time-series.

9 · Security note — portal authentication

Current state. The Tenant Admin and Platform Admin portals currently render without an enforced login gate (no middleware.ts, no session check). Until the auth middleware ships, these consoles must be network-restricted (e.g. IP allow-list at nginx). A Projexlight feature — *Portal authentication middleware* — tracks the fix: session verification, role-gated access (operator for /console, tenant-admin for /tenant, builder for /workspace), and ensuring privileged tokens are never reachable by an unauthenticated request.
