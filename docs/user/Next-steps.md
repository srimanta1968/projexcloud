● Big question, and it's the right one — you have ~70 SDKs that nobody outside this repo can yet discover or compose. Let me lay out an architecture and the innovative bit.

The keystone problem

Today an SDK is a package.json + TS source + a Postgres migration. None of that is consumable by an AI agent. Until each SDK publishes a machine-readable capability manifest, no
agent — cloud or CLI, yours or a customer's — can reason about what's available. So everything below depends on this one foundation.

Four-layer architecture

Layer 1 — Capability manifest per SDK (the foundation)

Each SDK ships an sdk-capability.json that declares:

- What it does — one-paragraph description (for embedding/semantic search)
- What it provides — endpoints, event types, data models, hooks, optional UI components
- What it consumes — events from other SDKs, infra (Postgres/Redis/Kafka), config keys
- Example scenarios — 3–5 short use-cases with code snippets
- Compliance posture — what regimes it satisfies (HIPAA, SOC 2, FedRAMP-ish)

Half of this can be auto-generated by scanning package.json, route registrations, events.ts, migration SQL. The other half (descriptions, scenarios) is hand-written once per SDK.

Layer 2 — Capability registry + MCP server (discovery)

A new @projexlight/sdk-registry package that:

- Scans all SDK manifests at build time → produces one JSON catalog
- Embeds each SDK's description (small open model) → enables semantic search
- Exposes an MCP server mounted at the api-gateway with tools like:
  - search_sdks(intent: string) — "I need consent management for healthcare" → ranked list
  - get_manifest(sdk_name) — full capability sheet
  - get_example(sdk_name, scenario) — copy-pasteable code
  - list_compatible_sdks(sdk_name) — what plays well together (derived from event consumes/produces)
  - scaffold(sdk_names: string[], app_name) — generate a starter project that wires them together

This makes every SDK addressable by any MCP-aware AI client — Claude Code, Cursor, Windsurf, Cline, custom agents — without you writing a plugin per tool. MCP is the universal
connector. You already have sdk-mcp-bridge and an mcp-server directory in the tree, so this isn't a leap.

Each blueprint = ordered SDK list + scaffold hints + sample data + demo workflow. AI uses these as starting points, then customizes per the customer's prompt.

Layer 4 — Two entry points for builders

Entry A — Cloud agent (no-code-ish, hosted)
Tenant goes to /build in their workspace. Types: "I want to build a claims-processing app for my auto-insurance team."
The cloud agent:

1. Searches blueprints → "Insurance claims intake" is the best match
2. Asks 2–3 clarifying questions (do you need photo evidence? do you settle in-app or via Stripe?)
3. Spawns an isolated sandbox inside the tenant's pool
4. Scaffolds the app, runs migrations, generates UI, seeds demo data
5. Hands the tenant a working URL within 5 minutes

Best for: non-developers, fast trials, "show me what's possible" demos.

Entry B — Local CLI + MCP (devs own the code)
Customer's developer runs:
npx @projexlight/cli init claims-app
cd claims-app
The CLI:

1. Bootstraps a local repo
2. Writes .claude/mcp.json (or cursor.mcp.json) pointing at the tenant's registry MCP, authed with the tenant's API key
3. Drops a CLAUDE.md with project context

Now their existing AI coding tool (Claude Code, Cursor, Windsurf — whichever they already use) has full SDK discoverability via MCP. The dev prompts: "Add evidence chain-of-custody
to the claim form." AI calls search_sdks("evidence chain of custody") → finds sdk-evidence, reads its example, writes the integration. The dev reviews, iterates, runs projex deploy →
ships to their tenant's pool.

Best for: dev teams who want code ownership, source control, custom logic.

Both entry points share the same registry, blueprints, and SDKs. Only the surface differs.

The innovative angle: vertical packs

Rather than treating each SDK as standalone, ship them in pre-composed vertical packs that bundle SDKs + compliance attestations + sample blueprints:

- Healthcare Pack — sdk-evidence + sdk-consent + sdk-data-rights + hdk-camera + sdk-conversation, pre-mapped to HIPAA + 21 CFR Part 11 controls
- FinServ Pack — sdk-audit + sdk-approval + sdk-policy + sdk-sovereign, pre-mapped to SOX + PCI-DSS
- Public Sector Pack — sdk-sovereign + sdk-onprem + sdk-audit + sdk-data-rights, pre-mapped to FedRAMP-Moderate + StateRAMP

When a tenant signs up they pick a pack (or "general purpose"). The pack determines:

- Which SDKs are pre-installed in their module_subscriptions
- Which blueprints show up in the /build surface
- Which compliance attestations the platform commits to
- Which guardrails the cloud agent enforces (HIPAA pack: agent refuses to scaffold anything that writes PHI to a non-encrypted column)

This turns the platform from "70 SDKs, figure it out" into "pick your industry, ship in a week."

Where to start

I'd build in this order:

1. Layer 1 + 2 first (registry + MCP). Without machine-readable manifests, none of the AI stories work. This is also the most reusable — it benefits internal devs today, not just
   future customers.
2. One vertical blueprint to validate the model end-to-end (pick the simplest one — "B2B SaaS analytics" or "RevOps CRM").
3. Entry B (local CLI + MCP) next, because it's cheaper to build than the hosted agent and serves the highest-ROI users (dev teams).
4. Entry A (cloud agent) last, once you've learned what blueprints actually need from the CLI experience.

Trade-off to flag: Layer 1 manifests are mostly hand-written prose per SDK. With ~70 SDKs that's a real authoring lift — maybe 1–2 days per SDK if you want them good enough for an AI
to compose against. The auto-generated parts (routes, events, deps) can be there in a week; the descriptions and scenarios are the long pole.

My recommendation

Start with a proof of concept: pick 5 SDKs that compose into one vertical (say sdk-crm + sdk-engagement + sdk-lead-scoring + sdk-campaign + connector-salesforce for RevOps CRM),
write manifests for those 5, build the registry + MCP for them, then create the local CLI flow. End-to-end demo: a dev runs projex init revops-crm, opens Claude Code, prompts "build
me a lead-routing workflow," AI uses the MCP to wire up the SDKs, dev deploys. Once that's working, you've validated the whole architecture and can scale to all 70 SDKs.
