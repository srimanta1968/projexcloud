ProjexCloud · Infrastructure

Production Deployment Guide

What an actual large-scale production system needs — and why the current “mini” test box is not that. Written from the running system’s real architecture.

Scope: moving ProjexCloud from the single 2-core / ~4 GB test EC2 box to a proper multi-tier production deployment. Read the “Known gaps” checklist before go-live.

The one thing to internalise Almost every performance compromise in the current stack exists because ClickHouse, Postgres, Redis, the api-gateway and three portals are all crammed onto one 2-core / 3.9 GB box. Production is not “the same box, bigger” — it is separate tiers. The test-box tuning (shrunken caches, disabled telemetry, 1 GB memory ceiling) must be reverted on real hardware or it will silently cripple it.

2. Target production topology

The current box runs all of the above in one Docker Compose stack. For production, split by failure domain and resource profile:

Edge / LB

nginx or a managed load balancer (ALB). TLS, WAF, rate limiting. Fronts N gateway replicas + the portals.

App tier

2+ api-gateway replicas behind the LB, plus the three portals. Stateless — scale horizontally. The admin-ops-token cache already uses Redis pub/sub for cross-replica invalidation, so multi-replica is a supported design.

Data tier — OLTP

Postgres on its own instance or a managed service (RDS/Aurora). Connection pooling (PgBouncer) in front.

Data tier — OLAP

Dedicated ClickHouse instance or a managed OLAP service. Never co-located with OLTP + app.

Cache / bus

Redis on its own instance or managed (ElastiCache). Used for caching and cross-replica invalidation.

Registry

registry-mcp alongside the app tier; its artifacts are currently bind-mounted (the untracked local-artifacts override).

Why separate ClickHouse On the test box ClickHouse pinned both cores at 200%+ and starved Postgres — the observed gateway DB timeouts were a scheduling problem, not a Postgres problem. Isolating OLAP removes that entire class of incident.

2A. Architecture model — modular monolith vs microservices

ProjexCloud today is a modular monolith, not microservices: one api-gateway process mounts all 76 SDKs (69 sdk-* + 7 hdk-*) as in-process route plugins. It already has two clean separation axes, which is why it is well-placed to extract services later:

AxisMechanism todayMeaning
Vertical — by domainEach SDK owns its own Postgres schema (identity., consent., billing., connector_*, …) — 76 schemas in one DB “Schema-per-service” — the logical microservice boundaries are already drawn
Horizontal — by tenantdb-runtime keeps a Map<pool_index, pg.Pool>; each pool_index (from the JWT’s admin_pool_index/app_pool_index) can point at a different Postgres cluster via routing.tenant_pool_map Tenants are already shardable across physical clusters — no code change to add a shard

Pod counts: current vs full microservices

Modular monolith (today)Full microservices (SDK-per-service)
Services / pods~7–9 app-tier (2 gateway + portals + registry) 76 services → ~150+ pods at 2 replicas each, + portals + a BFF/gateway + infra
Databases1 logical Postgres (76 schemas), shardable per tenant 76 databases (DB-per-service) × each tenant shard
Inter-SDK callsIn-process function calls (nanoseconds, transactional) Network RPC — retries, timeouts, tracing, versioned contracts
Cross-domain querySQL JOIN across schemas (~30 join sites exist) No cross-DB JOIN — needs API composition or data duplication (CQRS/events)
TransactionsSingle-DB ACIDDistributed (sagas / outbox)
Ops surface1 image, 1 deploy, 1 migration run76 pipelines, 76 migration owners, service mesh, per-service dashboards
Right whenNearly always — up to very large scaleSpecific team-ownership / independent-scale / blast-radius needs
Recommendation: do NOT go full microservices 76 services + 76 databases is a ~20× jump in operational surface for no benefit at current scale, and the ~30 cross-schema JOINs (persona, identity, webhook, lineage, meter, billing…) would each become a network call or a data-duplication problem. The monolith is the right default well past early scale.
The right path: strangler extraction Because every SDK already owns a schema, you can extract individual SDKs when one actually needs independent scale or isolation — without a rewrite. Extract the few hot/heavy ones first (candidates: sdk-ai-gateway, sdk-ingest, meter/OLAP, media/HDK), give each its own pod + its own database (promote its schema to a standalone DB, repoint that SDK’s dataService pool), and leave the rest in the gateway. Watch the cross-schema JOINs into the extracted schema — those are the seams to convert to API/event calls first.

How many containers / replicas

Today it is one host, 8 single-instance containers (one Compose stack). A real production deployment needs an orchestrator (Kubernetes / ECS / Swarm) or a load balancer across multiple hosts — the single-host Compose file does not do multi-replica by itself. Minimum counts for a small-but-highly-available launch:

ComponentNowMin for HAScale signal
api-gateway12+CPU / p95 latency → add replicas (stateless)
portal-workspace12Request volume
portal-tenant12Request volume
portal-console11–2Low (admin surface)
registry-mcp11–2Usually 1
Postgres11 primary + 1 standbyOr managed Multi-AZ (RDS/Aurora)
Redis11 primary + 1 replicaOr managed (ElastiCache) w/ failover
ClickHouse1 (starved)1 dedicatedCluster only at large OLAP scale
nginx / LB1Managed ALB, or 2× nginxEdge HA

Rough total for a HA launch: ~7–9 app-tier containers (2 gateway + 2+2+1 portals + 1 registry) across ≥2 hosts, plus the data tier — either 3 managed services (Postgres, Redis, ClickHouse) or ~5 self-managed containers (2 pg + 2 redis + 1 CH) on their own hosts. The app tier scales out with load; the data tier scales up (bigger instances) before it scales out.

Orchestration is a prerequisite for replicas Running 2+ of anything means moving off single-host Compose to Kubernetes / ECS / Swarm (or an LB fronting multiple Compose hosts). The gateway is designed for it — its ADMIN_OPS_TOKEN cache invalidates across replicas via Redis pub/sub — but the deploy tooling (deploy-service.sh) is single-host and would need to become a CI→registry→rollout pipeline.

4. ClickHouse: mini vs production config

The file infra/clickhouse/config.d/tuning.xml is a survival config for the 1.4 GB container. On a dedicated production box, most of it must be reverted — it trades away observability and query performance to fit tiny memory.

SettingMini box (now)Production (dedicated box)
*_log tables (metric_log, trace_log, asynchronous_metric_log, processors_profile_log) disabled merges couldn’t fit Re-enable. These are core observability — metrics history, query traces. Cheap on a big box.
uncompressed_cache_size0Restore (default 8 GB scale, or size to RAM)
mark_cache_size256 MBRaise substantially (default ~5 GB); 256 MB thrashes on real tables
index_mark_cache_size128 MBRaise (default ~5 GB)
max_server_memory_usage1 GB hard capRemove, or use the 0.9-of-RAM ratio
thread pools (schedule 16, max 256, concurrent 16)throttled for 2 coresRaise / defaults to use available cores
cap_add: [SYS_NICE]keepKeep — always correct; without it ClickHouse spams get_mempolicy
logging.xml (server log-file rotation)info level, 100M×3Keep; optionally allow more retention
cpus guardrail1.5 (co-located)Drop on a dedicated box
Silent carry-over risk If the mini profile follows a deploy to the big box, you get a 64 GB ClickHouse running with 256 MB caches, a 1 GB ceiling, and no telemetry — mysteriously slow, and no metrics to debug it. This is now env-selectable (implemented): tuning.xml is the small/co-located profile (default) and tuning.prod.xml is the dedicated-box profile (telemetry on, caches/memory at defaults, just SYS_NICE + a memory ratio). The compose file picks via CH_TUNING_FILE (plus CH_MEM_LIMIT / CH_CPUS). On the big box set in .env.prod: CH_TUNING_FILE=tuning.prod.xml CH_MEM_LIMIT=48g CH_CPUS=0.
Root-cause reminder The memory-drain incident was ClickHouse’s own *_log self-telemetry tables spiraling because cache config assumed a ~64 GB box inside a 1.4 GB container. On a correctly-sized dedicated box that spiral cannot happen — so the fix is “separate + defaults,” not “disable everything forever.”

5. Postgres & Redis

Postgres

  • Own instance / managed service; PgBouncer in front (the gateway opens many pools — per-tenant sharding + background workers).
  • The gateway auto-runs every SDK migration on boot — ensure the DB user has DDL rights and that a cold start against a fresh DB is part of the runbook.
  • Automated backups + PITR; test restore. Provisioned IOPS storage.

Redis

  • Own instance / managed with failover. Used for route cache and the admin-ops-token cross-replica invalidation channel — required for multi-replica gateways so a revoked ops-token stops working everywhere within Redis latency (not per-replica TTL).
  • Enable persistence if any cached state must survive restart.

6. Deploy pipeline

ProjexCloud is docker-compose based. It does not use crm-server.sh (that belongs to the separate ProjexCRM project).

Incremental redeploy of changed service(s) — the normal path

# on the prod host, from /home/ec2-user/projexcloud, with .env.prod present
scripts/setup/deploy-service.sh api-gateway
scripts/setup/deploy-service.sh api-gateway portal-console   # multiple
NO_PULL=1 scripts/setup/deploy-service.sh api-gateway         # skip git pull

It does git pull --ff-only origin main, then rebuilds only the named service image(s) and recreates just those containers, then health-gates the gateway. Builds are Turbo/BuildKit-incremental: the pnpm store and .turbo cache are persisted BuildKit cache mounts, so unchanged packages restore their dist/ from cache and only changed packages (+ dependents) recompile — a one-file change rebuilds in minutes.

No-build reconcile / boot / registry deploy

./deploy.sh up       # reconcile to desired state with current images (no build)
./deploy.sh deploy   # registry pull then up (when IMAGE_PREFIX/TAG set)
./deploy.sh ps | logs <svc>
Production build strategy Building on the prod host is fine for a single box but does not scale. For a real fleet, build images in CI, push to a registry (ECR), and deploy with ./deploy.sh deploy (image pull, no on-host build). The gateway Dockerfile already supports a scoped build (turbo run build --filter=@projexlight/api-gateway...) once the gateway’s package.json is confirmed to declare every SDK it imports.
New SDKs The build compiles all packages, but a new SDK is only served if it is a workspace:* dependency in the gateway package.json and registered via app.register(...) in services/api-gateway/src/app.ts. Forgetting the register line ships a silently-missing route — add both.

7. Secrets & configuration

  • .env.prod holds all secrets (JWT_SECRET, ADMIN_OPS_TOKEN, DB password, etc.). It is untracked — never commit it. In production, source secrets from a manager (SSM Parameter Store / Secrets Manager), not a file on the box.
  • One operator secret: ADMIN_OPS_TOKEN guards all /admin/* routes (the former FEDERATION_ADMIN_TOKEN was consolidated into it). It also has a DB-backed active-token set with cross-replica invalidation, so short-lived tokens can be minted/revoked without a redeploy.
  • Add .env.prod to .gitignore so a stray git clean can never delete production secrets.

8. Auth & sessions

  • Default-deny gate (services/api-gateway/src/plugins/authGate.ts): every request needs a valid tenant JWT unless the path is public (auth/health/well-known/storm/metrics), SAML, an OAuth callback, a signature-verified webhook, admin (self-guards via ADMIN_OPS_TOKEN), or a WebSocket upgrade.
  • Kill-switch: AUTH_GATE_MODE = enforce (default) | report | off. report logs would-be blocks without blocking; off disables the gate. Flip without a rebuild via up -d --force-recreate api-gateway.
Fix before real users at scale JWT is 7-day expiry with no refresh endpoint. Tokens silently die at 7 days and the client replays the dead one → 401 on every call until re-login. For production, add a short-lived access token + rotating refresh token (httpOnly cookie) and a /api/auth/refresh route, or at minimum client-side proactive re-auth. See the auth findings for the full design.

9. Observability & logging

  • Re-enable ClickHouse telemetry on the dedicated box (see §4) — you want metric_log/trace_log/query_log for performance debugging.
  • /metrics (Prometheus) is exposed on the gateway — scrape it. /health and per-SDK */health endpoints are public for load-balancer checks.
  • nginx logrotate is broken on the current box: logrotate renamed access.log but never signalled nginx, so nginx still writes to the old handle and the live access.log is stale/missing. Fix with a postrotate that runs nginx -s reopen (or systemctl reload nginx). Do this before relying on access logs in prod.
  • Centralise logs (CloudWatch / Loki) and alert on disk usage — the test box hit 86%; build cache and images grow.

10. Known gaps — pre-production checklist

Concrete items surfaced during this system’s hardening. Close these before a real production launch:

  • Separate ClickHouse onto a dedicated instance and switch to a production ClickHouse profile (telemetry on, caches/memory at defaults, keep SYS_NICE).
  • done ClickHouse config split — tuning.xml (small) / tuning.prod.xml (dedicated) selected by CH_TUNING_FILE, so test settings can’t silently follow a deploy. Set the prod profile when you provision the big box.
  • Separate Postgres & Redis onto their own instances / managed services; add PgBouncer.
  • JWT refresh flow — short access token + rotating refresh token + /api/auth/refresh.
  • Per-handler tenant-scoping — the auth gate authenticates but does not yet scope every SDK query by tenant_id; close the residual cross-tenant read (IDOR) risk on the newly-gated routes.
  • WebSocket auth — the two WS upgrade routes are gate-exempt; implement Sec-WebSocket-Protocol token auth.
  • Fix nginx logrotate (nginx -s reopen in postrotate).
  • CI image builds + registry deploy instead of on-host builds for a fleet.
  • Secrets from a manager (SSM / Secrets Manager); add .env.prod to .gitignore.
  • Backups + restore drill for Postgres; disk-usage alerting on every box.
  • Multi-replica gateway behind a load balancer; verify Redis-backed ops-token invalidation works across replicas.
