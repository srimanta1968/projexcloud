ProjexCloud ↔ ProjexLight Integration

Make ProjexLight's AI code generator reuse ProjexCloud's 75 SDKs (538 APIs) instead of rebuilding them, and let a customer start a ProjexCloud-backed project from either product. The mechanism: ProjexCloud publishes a machine-readable SDK catalog that ships inside every CLI export, so the codegen LLM discovers and reuses SDK APIs by construction.

Status · DRAFT v0.1 — for review
Date · 2026-07-21
Owner · Platform / Developer Experience
Scope · Plan + contracts only; implementation follows per §9
What this PRD commits to. (1) The load-bearing piece is a machine-readable SDK catalog generated in ProjexCloud from the same source as the API reference (qa-apis.json), synced into ProjexLight's MCP toolkit (ai-appgen/mcp/dist/data/) so it is bundled into every CLI export. (2) The exported build instruction gains a reuse rule — consult the catalog first; reuse the SDK via the gateway; only generate custom code for gaps. (3) A deep-link on-ramp lets ProjexCloud's Build page create a seeded ProjexLight project without either product holding the other's credentials. (4) Recommendation: Phase 1 first (catalog + reuse rule — makes reuse actually happen, ProjexCloud-side, ships value alone); Phase 2 (the on-ramp) second.

1 · TL;DR

The problem
ProjexLight can't see ProjexCloud's SDKs
Its reuse engine only searches the project's own resources. So a ProjexCloud-targeted project regenerates a CRM / auth / scheduler from scratch — the opposite of reuse.
The fix (Phase 1)
Bundle the SDK catalog into every export
Publish sdk-catalog.json in ProjexCloud → sync into ai-appgen/mcp/dist/data/ → it ships with every CLI export → a reuse rule tells the LLM to consult it and call the gateway.
The on-ramp (Phase 2)
Create a ProjexLight project from ProjexCloud
A "Create in ProjexLight" button on /build hands the composed plan over via a one-time deep-link token — no cross-product key custody.
Recommendation. These solve different halves. Phase 1 (catalog + reuse rule) is what makes reuse happen and is cheap — do it first. Phase 2 (the on-ramp) is the premium funnel and only pays off once Phase 1 exists.
P0 — Three independent consumption modes (foundational principle). ProjexCloud and ProjexLight compose three ways, and each must stand on its own:
ModeProjexLight?ProjexCloud SDKs?How the developer works
A · DirectnoyesDownload the SDK catalog, grab an API key + base URL, and call the APIs from their own project/tooling (hand-code, or feed the catalog to their own AI assistant). ProjexCloud is a self-serve API product.
B · AcceleratedyesyesUse the catalog + key + base URL with the CLI export + ProjexLight; the AI builder reuses SDKs (useProjexCloudSdks: true).
C · ProjexLight-onlyyesnoGenerate everything from scratch in ProjexLight — exactly what it does today (useProjexCloudSdks: false, the default).
ProjexCloud is an opt-in accelerator, never a dependency (Mode C needs no ProjexCloud account); and it is usable entirely on its own (Mode A needs no ProjexLight). Every decision point links a "Why pre-built SDKs?" benefits reference. The catalog work (FR1) is the shared asset behind Modes A and B.

2 · Background & Problem Statement

2.1 · The two products today

ProjexLight · ai-appgen
Generic AI app generator
React + Express (REST) + Postgres. Describe an app → plan as Epic → Feature → Scenario (BDD) → Task → export a scaffold → a local CLI agent generates code task-by-task.
  • POST /api/projects; JWT + encrypted platform API key + MCP_SESSION_TOKEN.
  • Discovery = embeddings search over the project's own resources (text-embedding-3-small, "reuse before generate").
  • Export = Sprint Wizard → ZIP → S3; bundles Dev-MCP :8766 + Test-MCP :8000.
  • Proven savings: −50% tokens · −84% startup · str_replace 100%→0% · ~50% fewer sessions.
ProjexCloud
75 reusable SDKs · 538 gateway APIs
One Fastify gateway mounting ~90 SDKs; Postgres pools + Redis + ClickHouse; portals behind nginx at cloud.projexlight.com.
  • Default-deny gate: a valid tenant JWT gates every non-public route.
  • In-portal discovery: Workspace → Build → POST /api/build/plan composes {recommended_sdks, custom_work, vertical_pack, complexity}.
  • Reference already generated: docs/v3.1/api_docs/index.html + machine data scripts/qa-matrix/qa-apis.json.

2.3 · The gap

ProjexLight discovery  ─►  embeds/searches the PROJECT's own resources only
ProjexCloud catalog    ─►  75 SDKs / 538 APIs  ── NOT visible to ProjexLight codegen
ProjexCloud /build     ─►  composes an SDK plan  ── but does NOT create a ProjexLight project
Consequence. The codegen LLM cannot reuse ProjexCloud SDKs because it never learns they exist. Reuse — the entire economic argument — does not happen: weeks of rebuild, wasted tokens, and re-implemented (weaker) identity/consent/RLS enforcement.

3 · Goals & Non-Goals

Goals
  • G0 · Optional by design — codegen works fully standalone and accelerated; the customer chooses per project (default = standalone). ProjexCloud is never a hard dependency.
  • G1 · Reuse — codegen discovers & reuses ProjexCloud SDKs (calls the gateway) instead of generating backends, when opted in.
  • G2 · On-ramp — idea → seeded ProjexLight project + downloadable scaffold, starting inside ProjexCloud.
  • G3 · No secret custody — neither product stores the other's credentials (deep-link hand-off).
  • G4 · Preserve the contract — generated app calls the gateway with the tenant JWT; gated/metered/audited/per-pool isolation untouched.
  • G5 · Zero drift — catalog auto-generated from the same source as the API reference.
Non-Goals
  • Rebuilding ProjexLight's codegen engine or refinement wizard.
  • Merging the two products or their billing.
  • The customer-facing documentation (the next deliverable after this PRD).
  • Vertical connectors or agent-runtime changes.

5.2 · Phase 1 requirements — reuse foundation PHASE 1

FR0 · Opt-in decision + two code-generation modes (gates everything below)
A useProjexCloudSdks choice is captured at the decision point — in ProjexLight project setup (a "Use ProjexCloud pre-built SDKs?" step) and/or ProjexCloud's /build — and persisted in .projexlight/config/export-config.json (default false = standalone).
Mode ON · Accelerated
FR1–FR4 apply — catalog bundled, reuse rule in build_instruction.md, plan seeds "reuse" tasks. Codegen reuses SDKs via the gateway.
Mode OFF · Standalone default
Exactly today's ProjexLight behavior — no catalog, no reuse rule, every task generates from scratch, no ProjexCloud account required. Nothing regresses.
The decision UI links FR9 (benefits reference) so the choice is informed. Reversible: a later export can flip the flag; existing generated code is untouched.
FR1 · Machine-readable SDK catalog (Mode ON)
Generated by a new step in scripts/qa-matrix/ (the pipeline that builds the API reference), from qa-apis.json + the group map (§2.2). Published next to the API reference and mirrored to the portals. Per SDK: { sdk, group, summary, api_count, apis:[{method, endpoint, requiresAuth, summary, payload_shape, fieldEnums, dependsOn}], reuse_when:[keywords], docs_url }. Public, non-sensitive — API surface only, no data, no secrets.
FR2 · Bundle the catalog into the CLI export (primary distribution)
Sync into the MCP toolkit: CI copies sdk-catalog.json into ai-appgen/mcp/dist/data/sdk-catalog.json. mcp/dist is the toolkit shipped inside every CLI export (the setup-all.sh / compose / data / docs / templates bundle), so every exported project carries the catalog on disk. Serve it from the Dev-MCP (recommended): a projexlight_get_sdk_catalog tool / GET /api/sdk-catalog on :8766 reading data/sdk-catalog.json, so the LLM can query "which SDK/API covers X?" as a tool call. Freshness: sync on version bump; exports pin the version they shipped with. (Enhancement:) also embed entries into ProjexLight's embeddings table as resource_type='projexcloud_sdk' to rank SDKs in its reuse search.
FR3 · Reuse rule in the exported build instruction
mcp/dist/templates/build_instruction.md (which becomes the exported build guidance) gains:
"Before generating any backend, service, or data model, consult the ProjexCloud SDK catalog at mcp-server/data/sdk-catalog.json (or call the Dev-MCP get_sdk_catalog tool). If an SDK covers the capability, REUSE it: call the gateway at <gateway_base_url>/api/… with the tenant JWT — do not write a new backend. Only generate custom code for capabilities no SDK provides."
Plus the API-reference URL and a short "authenticate to the gateway" note (tenant signup/login → JWT → Authorization: Bearer). Net effect: the LLM discovers all 538 SDK APIs from the shipped catalog and decides reuse-vs-generate per capability. (In Mode OFF this rule is absent — the standard "generate everything" guidance applies.)
FR9 · "Why pre-built SDKs?" benefits reference (informs the FR0 choice)
A customer-facing page in the ProjexCloud docs (docs/v3.1/developer-hub/why-sdks.html, mirrored to the portals + linked from the landing page like the API reference) that lets a customer decide with vs without, stating both sides honestly:
Reuse (Mode ON)
Ships in minutes not weeks; −50% tokens / ~50% fewer sessions on top of ProjexLight's baseline; 538 production-grade APIs across 9 domains; identity/RLS/ABAC/consent enforced at the SDK gate (not re-implemented in generated code); metered/audited/replayable; no backend to maintain; canonical-ID model (no PII duplication).
Standalone (Mode OFF)
Full control of every line; no ProjexCloud account or runtime dependency; no per-call metering; best when the app is offline-only, air-gapped without ProjexCloud, or intentionally self-contained.
Includes a short decision matrix ("choose reuse when… / choose standalone when…") + a per-group summary of what each SDK family gives you. Linked from ProjexLight's opt-in step, ProjexCloud /build, the export's build_instruction.md, and the Developer Hub.
FR4 · Reuse surfaced in the plan
Extend POST /api/build/plan's recommended_sdks[] with, per SDK, the concrete apis[] + docs_url from the catalog — so the bootstrap (and Phase 2 seeding) have exact endpoints, not just names.

FR5 · "Create in ProjexLight" CTA
on the /build result, after a plan is composed.
FR6 · Deep-link hand-off
ProjexCloud mints a one-time, short-TTL, signed token {plan, tenant_ref, return_url, nonce} → redirect to ProjexLight /import?handoff=…; ProjexLight verifies server-to-server; user authenticates with their own account. No API-key custody.
FR7 · Seed the project
Create project (POST /api/projects); one Feature per capability; each recommended SDK → a "reuse" Task ("integrate <sdk> via the gateway", carrying apis[] + docs_url); each custom_work[] → a normal generate Task.
FR8 · Export + return
Trigger the Sprint Export; return the S3 download link (optionally deep-link back to ProjexCloud's return_url).

7 · User Flows

Flow A — start in ProjexCloud
Phase 1 + Phase 2
  1. Workspace → Build → describe app → catalog-enriched plan.
  2. Create in ProjexLight → deep-link + one-time token.
  3. Authenticate → project + Epics/Features/Tasks seeded, SDKs as reuse tasks.
  4. Export → scaffold ships the catalog + reuse rule.
  5. Local: ./setup-all.sh (Dev-MCP :8766, Test-MCP :8000) → run the CLI agent → backend tasks resolve by calling ProjexCloud gateway APIs; custom tasks generate UI/domain code.
Flow B — start in ProjexLight
Phase 1 only
  1. Create a project in ProjexLight; refinement wizard → PRD.
  2. Export bundles the catalog (mcp/dist/data/) + reuse rule.
  3. Codegen consults the catalog → reuses ProjexCloud SDKs.
  4. (Enhancement) discovery search ranks ProjexCloud SDKs as reuse candidates.

8 · Security & Trust Boundary

  • No key custody — Phase 2 uses a one-time, signed, short-TTL hand-off token verified server-to-server; neither product stores the other's credentials. (Vaulting a ProjexLight key via sdk-secrets is the explicit non-preferred fallback.)
  • Catalog is public API-surface only — no data, no secrets; safe to publish, bundle, and embed.
  • Runtime isolation unchanged — the generated app authenticates to the gateway with the tenant JWT; every reused SDK call is gated/metered/audited and lands in the tenant's pool.
  • PII boundary honored — reuse tasks reference canonical IDs (person_id, persona_id) per AIM; identity data is never duplicated into the generated app.
  • Tenant/account linking (open question §11) — how a ProjexCloud tenant maps to a ProjexLight account/entitlement.

11 · Open Questions

  1. External API contract — does ProjexLight expose project-create + import + export to external callers with token auth, or only via the in-app wizard + MCP session token? (Determines M7 shape.)
  2. Account linking — how does a ProjexCloud tenant identify/authorize itself to ProjexLight (shared IdP? entitlement mapping?).
  3. Billing split — ProjexLight meters codegen ($/min); ProjexCloud meters runtime SDK calls — confirm no double-charge and where the reuse "credit" lands.
  4. Discovery ingestion — batch-embed the catalog into ProjexLight's embeddings table (preferred) vs a live federated search against a ProjexCloud catalog endpoint.
  5. Versioning — how catalog version bumps propagate to already-exported projects (pin vs auto-refresh).
