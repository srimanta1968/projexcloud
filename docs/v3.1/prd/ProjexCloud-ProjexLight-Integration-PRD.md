## 1 · TL;DR

**ProjexLight** (repo: `ai-appgen`) is a generic, multi-provider AI *app generator*: a customer describes an app, ProjexLight plans it as Epics → Features → Scenarios → Tasks, exports a scaffold, and a local CLI agent generates the code task-by-task.

**ProjexCloud** is a library of **75 reusable SDKs (538 gateway APIs)** — identity, CRM, scheduling, outreach, billing, agents, etc. — that a generated app should *consume* instead of rebuilding.

**The problem:** ProjexLight's reuse engine only searches *the project's own* embeddings. It has **no knowledge of ProjexCloud's SDK catalog**, so a ProjexLight project targeting ProjexCloud regenerates a CRM / auth / scheduler from scratch — the opposite of reuse.

**The integration makes ProjexLight aware of ProjexCloud's SDKs and lets a customer start a ProjexCloud-backed project from either product.** Delivered in two phases:

- **Phase 1 — Reuse foundation (load-bearing):** publish a machine-readable **SDK catalog**, register it into ProjexLight's discovery, and add a **bootstrap reuse rule** so codegen calls ProjexCloud APIs rather than writing new backends.
- **Phase 2 — On-ramp (funnel):** a **"Create project in ProjexLight"** action on ProjexCloud's `/build` result, via a **deep-link hand-off** (no cross-product key custody).

**Recommendation:** Phase 1 first — it is what makes reuse actually happen and is cheap. Phase 2 is the premium UX and only pays off once Phase 1 exists.

> **P0 — ProjexCloud SDKs are OPTIONAL (foundational principle).** ProjexLight code generation must work **fully standalone** (generate everything from scratch — its default today) *and* **accelerated** (reuse ProjexCloud SDKs). The customer chooses **per project**; the choice drives whether the catalog + reuse rule ship. A customer who declines needs **no ProjexCloud account** and gets exactly today's ProjexLight behavior. To make an informed choice, every decision point links a **"Why pre-built SDKs?" benefits reference**. ProjexCloud is an opt-in accelerator, never a dependency.

## 2 · Background & problem statement

### 2.1 The two products today

**ProjexLight (`ai-appgen`)** — React + Express (REST) + Postgres.
- Auth: JWT (register/login) + an **encrypted platform API key** + `MCP_SESSION_TOKEN` (already present in exports' `mcp-config.json` / `.env`).
- Project creation: `POST /api/projects` (name + description); a 15-step **Project Refinement Wizard** turns a short idea into a PRD.
- Hierarchy: **Epic → Feature (Background) → Scenario (Gherkin BDD, `bdd_steps` JSONB) → Task.**
- Discovery/reuse: `POST /api/embeddings/projects/{projectId}/search` — cosine similarity (`text-embedding-3-small`, threshold 0.7) over **the project's own resources**; "search existing codebase FIRST, reuse before creating."
- Export: **Sprint Export Wizard → ZIP → S3 → download URL.** ZIP carries `.claude/instructions/bootstrap.md`, `.projexlight/context/*`, an optional bundled **Dev-MCP (`:8766`) + Test-MCP (`:8000`)** and Postgres via generated `docker-compose.yml`.
- Codegen loop (per task): `init_session` → `get_instruction` → *write API-definition JSON first* → generate code → validate (dev-MCP standards + test-MCP API tests) → `complete_task`.
- Savings (from `ACTUAL_TOKEN_EFFICIENCY_ANALYSIS.md`): **−50% total tokens, −84% startup overhead, str_replace failures 100%→0%, ~50% fewer sessions.**

**ProjexCloud** — one Fastify **api-gateway** mounting ~90 SDKs; Postgres pools + Redis + ClickHouse; three portals behind nginx at `cloud.projexlight.com`.
- Gateway is a **default-deny gate**: a valid **tenant JWT** is required except for the public allowlist.
- In-portal discovery: **Workspace → Build** → `POST /api/build/plan` (`apps/tenant-workspace/app/api/build/plan/route.ts` + `lib/build/planLlm.ts`) → Claude composes `{ recommended_sdks[], custom_work[], clarifying_questions[], vertical_pack, complexity }` from the ~88-SDK catalog, with foundation-injection + dependency closure.
- Reference assets already generated by `scripts/qa-matrix/*`: the human **API reference** (`docs/v3.1/api_docs/index.html`) and the machine data `scripts/qa-matrix/qa-apis.json` (SDK → endpoint → method → auth → payload → `dependsOn`/cache → errorCases → fieldEnums).
- **75 SDKs / 538 APIs**, grouped:

  | Group | SDKs | APIs |
  |---|---|---|
  | Platform & Multi-Tenancy | 20 | 133 |
  | Outreach & Communication | 8 | 111 |
  | CRM & Engagement | 8 | 68 |
  | Governance, Consent & Security | 10 | 56 |
  | Identity & Access (AIM) | 6 | 55 |
  | AI & Agents | 7 | 53 |
  | Native HDK (mobile/edge) | 11 | 28 |
  | Connectors & Integration | 1 | 18 |
  | Billing, Metering & Analytics | 4 | 16 |

### 2.2 The gap

```
ProjexLight discovery  ──►  embeds/searches the PROJECT's own resources only
ProjexCloud catalog    ──►  75 SDKs / 538 APIs  ── NOT visible to ProjexLight codegen
ProjexCloud /build     ──►  composes an SDK plan  ── but does NOT create a ProjexLight project
```

Result: the codegen LLM cannot reuse ProjexCloud SDKs because it never learns they exist. Reuse — the entire economic argument — does not happen.

### 2.3 Why it matters

- **Reuse is the value prop.** 538 production-grade, gated/metered/audited APIs already exist. Regenerating even a fraction wastes weeks and tokens and ships weaker code.
- **Compounding with ProjexLight's own savings.** ProjexLight already cuts tokens ~50%; reusing whole SDKs instead of generating them multiplies that.
- **Correctness & compliance.** ProjexCloud enforces identity/RLS/ABAC/consent *at the SDK gate*. A hand-generated backend re-implements these — badly.

## 3 · Goals & non-goals

### 3.1 Goals
- **G0 — Optional by design:** ProjexLight codegen works fully standalone *and* accelerated-with-SDKs; the customer chooses per project (default = standalone). ProjexCloud is never a hard dependency. *(See P0.)*
- **G1 — Reuse:** ProjexLight codegen discovers and reuses ProjexCloud SDKs (calls the gateway) instead of generating equivalent backends — **when the customer opts in.**
- **G2 — On-ramp:** a customer can go from *app idea* to *seeded ProjexLight project + downloadable scaffold* starting inside ProjexCloud.
- **G3 — No cross-product secret custody:** ProjexCloud does not store ProjexLight credentials (prefer deep-link hand-off).
- **G4 — Preserve the contract:** the generated app calls the gateway with the tenant JWT; gated/metered/audited/per-pool isolation is untouched.
- **G5 — Zero drift:** the SDK catalog is auto-generated from the same source as the API reference (`qa-apis.json`), never hand-maintained.

### 3.2 Non-goals
- Rebuilding ProjexLight's codegen engine or its refinement wizard.
- Merging the two products or their billing.
- Shipping the customer-facing *documentation* (that is the next deliverable after this PRD).
- Vertical-specific connectors or agent runtime changes.

## 5 · Proposed solution

### 5.1 Architecture (two phases)

```
Phase 1 — Reuse foundation (catalog bundled into the CLI export)
  ProjexCloud (source of truth)              ProjexLight (ai-appgen)
  ┌────────────────────────┐   sync/CI   ┌──────────────────────────────┐
  │ qa-apis.json           │ ──────────► │ mcp/dist/data/               │
  │   → sdk-catalog.json   │             │     sdk-catalog.json         │
  │   (public, versioned)  │             │ mcp/dist/templates/          │
  └────────────────────────┘             │     build_instruction.md ◄── REUSE RULE
                                          └──────────────┬───────────────┘
                                                         │ CLI export bundles mcp/dist
                                                         ▼
                              Exported project ships: mcp-server/data/sdk-catalog.json
                                                       + build_instruction reuse rule
                                                         │
                              codegen LLM reads catalog ─┘ → reuses SDK via gateway,
                              (or Dev-MCP get_sdk_catalog)   generates only custom work

Phase 2 — On-ramp (deep-link, no key custody)
  ProjexCloud /build ──plan──► one-time token ──deep-link──► ProjexLight
                                                    │ user authenticates
                                                    ▼
                              create project + seed Epics/Features/Tasks
                              (each recommended SDK → a "reuse" task)
                                                    │
                              Sprint Export → S3 ──download link──► user
```

### 5.2 Phase 1 — Reuse foundation (load-bearing)

**FR0 · Opt-in decision + two code-generation modes (the gate for everything below).**
- A **`useProjexCloudSdks` choice** is captured at the decision point — in **ProjexLight project setup** (a "Use ProjexCloud pre-built SDKs?" step in the refinement wizard) and/or **ProjexCloud's `/build`** (opt in from the composed plan). Persisted in **`.projexlight/config/export-config.json`** as `useProjexCloudSdks: boolean` (default: **false** — standalone).
- **Mode ON — Accelerated:** FR1–FR4 apply — the catalog is bundled, the reuse rule ships in `build_instruction.md`, and the plan seeds "reuse" tasks. Codegen reuses ProjexCloud SDKs via the gateway.
- **Mode OFF — Standalone (default):** exactly today's ProjexLight behavior — **no** catalog bundled, **no** reuse rule, every task is a normal "generate" task, **no ProjexCloud account required**. Nothing about the standalone path regresses.
- The decision UI (both products) links **FR9 (the benefits reference)** so the user chooses informed. The choice is reversible: a later export can flip the flag (adds/removes the catalog + reuse rule; existing generated code is untouched).

**FR1 · Machine-readable SDK catalog (`sdk-catalog.json`).** <span>(Mode ON only.)</span>
- Generated by a new step in `scripts/qa-matrix/` (same pipeline that builds the API reference), from `qa-apis.json` + the group map in this PRD (§2.1).
- Published next to the API reference and mirrored to the portals (same pattern as `index.html`).
- Schema (per SDK): `{ sdk, group, summary, api_count, apis:[{ method, endpoint, requiresAuth, summary, payload_shape, fieldEnums, dependsOn }], reuse_when:[keywords], docs_url }`.
- Public, non-sensitive (API surface only — no secrets, no data).

**FR2 · Bundle the catalog into the CLI export (the primary distribution mechanism).**
- **Source of truth:** the catalog is generated and versioned in ProjexCloud (FR1) and published next to the API reference.
- **Sync into the MCP toolkit:** a sync step copies `sdk-catalog.json` into **`ai-appgen/mcp/dist/data/sdk-catalog.json`**. `mcp/dist` is the MCP toolkit that ships *inside every CLI export* (the `setup-all.sh` / compose / `data` / `docs` / `templates` bundle), so **every exported project automatically carries the catalog on disk** — no per-project fetch, works offline/air-gapped.
- **Serve it from the Dev-MCP (optional but recommended):** expose a `projexlight_get_sdk_catalog` tool / `GET /api/sdk-catalog` on the Dev-MCP (`:8766`) reading `data/sdk-catalog.json`, so the codegen LLM can query "which SDK/API covers X?" as a tool call, not just read a file.
- **Freshness:** the sync runs on catalog version bump (CI in ProjexCloud pushes to the `ai-appgen/mcp/dist/data` path); exported projects pin the version they shipped with and can refresh by re-running the export wizard.
- *(Enhancement, not required for MVP):* also embed each entry into ProjexLight's `embeddings` table as `resource_type='projexcloud_sdk'` so its cosine-similarity reuse search ranks ProjexCloud SDKs alongside project-local resources.

**FR3 · Reuse rule in the exported build instruction.**
- **`ai-appgen/mcp/dist/templates/build_instruction.md`** (the template that becomes the exported build guidance / bootstrap) gains an explicit rule:
  > *"Before generating any backend, service, or data model, consult the ProjexCloud SDK catalog at `mcp-server/data/sdk-catalog.json` (or call the Dev-MCP `get_sdk_catalog` tool). If an SDK covers the capability, REUSE it: call the gateway at `<gateway_base_url>/api/…` with the tenant JWT — do not write a new backend. Only generate custom code for capabilities no SDK provides."*
- Include the API-reference URL and a short "authenticate to the gateway" note (tenant signup/login → JWT → `Authorization: Bearer`).
- Net effect: **the LLM discovers all 538 SDK APIs from the shipped catalog and decides, per capability, reuse-vs-generate** — the core of the integration.
- *(In Mode OFF this rule is absent — the build instruction is the standard "generate everything" guidance.)*

**FR9 · "Why pre-built SDKs?" benefits reference (informs the FR0 choice).**
- A concise, customer-facing page in the ProjexCloud docs (e.g. `docs/v3.1/developer-hub/why-sdks.html`, also mirrored to the portals + linked from the landing page like the API reference) that lets a customer decide **with vs without**. It states, honestly, both sides:
  - **Reuse (Mode ON):** ships in minutes not weeks; **&minus;50% tokens / ~50% fewer sessions** on top of ProjexLight's baseline; 538 production-grade APIs across 9 domains; **identity / RLS / ABAC / consent enforced at the SDK gate** (not re-implemented, badly, in generated code); metered/audited/replayable; no backend to maintain; canonical-ID data model (no PII duplication).
  - **Standalone (Mode OFF):** full control of every line; **no ProjexCloud account or runtime dependency**; no per-call metering; best when the app is offline-only, air-gapped without ProjexCloud, or intentionally self-contained.
  - A short **decision matrix** ("choose reuse when… / choose standalone when…") and a per-group summary of what each SDK family gives you.
- Linked from: ProjexLight's opt-in step, ProjexCloud `/build`, the export's `build_instruction.md`, and the Developer Hub.

**FR4 · Reuse surfaced in the plan.**
- ProjexCloud `/api/build/plan` already emits `recommended_sdks[]`. Extend the plan object with, per SDK, the concrete `apis[]` and `docs_url` from the catalog, so downstream (bootstrap or Phase 2 seeding) has the exact endpoints.

### 5.3 Phase 2 — On-ramp (deep-link hand-off)

**FR5 · "Create project in ProjexLight" CTA** on the `/build` result page (after a plan is composed).

**FR6 · Deep-link hand-off (preferred over key custody).**
- ProjexCloud mints a **one-time, short-TTL, signed token** carrying `{ plan, tenant_ref, return_url, nonce }` and redirects to ProjexLight (`/import?handoff=<token>`).
- ProjexLight validates the token against a ProjexCloud verification endpoint, the user authenticates with their **own** ProjexLight account, and the plan is consumed. **No ProjexLight API key is ever stored in ProjexCloud.**

**FR7 · Seed the project from the plan.**
- ProjexLight creates the project (`POST /api/projects`) and seeds the hierarchy from the plan: one **Feature per capability**; each **recommended ProjexCloud SDK → a "reuse" Task** whose instructions say *"integrate `<sdk>` via the gateway,"* carrying the SDK's `apis[]` + `docs_url` (from FR1/FR4); each **`custom_work[]` item → a normal generate Task**.
- "reuse" Tasks are typed so codegen calls the gateway instead of generating a backend.

**FR8 · Export + return.**
- Trigger the Sprint Export; return the S3 download link to the user (in ProjexLight, optionally deep-linked back to ProjexCloud's `return_url`).

### 6.1a The opt-in flag (`export-config.json`)
```jsonc
// .projexlight/config/export-config.json — the FR0 switch
{
  "exportMode": "new_repository",
  "useProjexCloudSdks": false,               // default = standalone; true = accelerated
  "projexCloudCatalogVersion": "2026.07.21", // pinned when useProjexCloudSdks=true
  "selectedPurposes": [ /* … */ ]
}
```
When `false`: the export omits `sdk-catalog.json` and the reuse rule — pure standalone ProjexLight. When `true`: both ship, pinned to `projexCloudCatalogVersion`.

### 6.2 Deep-link hand-off token (Phase 2)
```jsonc
// ProjexCloud mints; ProjexLight verifies via ProjexCloud endpoint
{
  "iss": "projexcloud", "aud": "projexlight",
  "nonce": "<single-use>", "exp": "<now+10m>",
  "tenant_ref": "<opaque tenant handle, not PII>",
  "return_url": "https://cloud.projexlight.com/workspace/build?handoff=done",
  "plan": { "summary": "...", "vertical_pack": "revops", "complexity": "medium",
            "recommended_sdks": [ { "sdk": "sdk-crm", "apis": [ /* … */ ], "docs_url": "…" } ],
            "custom_work": [ "admin dashboard UI", "vertical pricing rules" ] }
}
```

## 7 · User flows

**Flow A — start in ProjexCloud (Phase 2 + Phase 1).**
1. Workspace → Build → describe app → `/api/build/plan` composes the plan (now catalog-enriched, FR4).
2. Click **Create in ProjexLight** → deep-link with one-time token (FR6).
3. Authenticate in ProjexLight → project + Epics/Features/Tasks seeded, SDKs as reuse tasks (FR7).
4. Export → download scaffold; `bootstrap.md` carries the reuse rule + catalog (FR3).
5. Local: `./setup-all.sh` (Dev-MCP `:8766`, Test-MCP `:8000`) → run the CLI agent → **backend tasks resolve by calling ProjexCloud gateway APIs**, custom tasks generate UI/domain code.

**Flow B — start in ProjexLight (Phase 1 only).**
1. Create a project in ProjexLight; refinement wizard → PRD.
2. Discovery search now surfaces ProjexCloud SDKs as reuse candidates (FR2).
3. Export includes the catalog + reuse rule (FR3); codegen reuses ProjexCloud SDKs.

## 8 · Security & trust boundary
- **No key custody:** Phase 2 uses a one-time, signed, short-TTL hand-off token verified server-to-server; ProjexCloud never stores ProjexLight credentials, and vice-versa. (Fallback A1 — ProjexCloud vaulting a ProjexLight API key via `sdk-secrets` — is explicitly the *non-preferred* option.)
- **Catalog is public API-surface only** — no data, no secrets; safe to publish + embed.
- **Runtime isolation unchanged:** the generated app authenticates to the gateway with the tenant JWT; every reused SDK call is gated/metered/audited and lands in the tenant's pool (per §12 of Architecture).
- **PII boundary honored:** reuse tasks reference canonical IDs (`person_id`, `persona_id`) per AIM; no identity data is duplicated into the generated app.
- **Tenant/account linking** (open question §11): how a ProjexCloud tenant maps to a ProjexLight account/entitlement.
