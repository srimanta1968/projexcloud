Header Contract & Tenant Request Authentication

One header-resolution contract shared by four request builders, the fixes required to make it trustworthy across the Dev MCP, the Test MCP and the ProjexLight UI, and the case for — and against — letting a tenant require its own custom header as a security layer on ProjexCloud SDK APIs.

Status Draft v0.1 Date 2026-08-06 Owner Platform / QA Automation Related Analyze.md (A–G), MUST-70, MUST-38, MUST-62, EP-386
Why this document exists. Four programs build an HTTP request from the same API definition. A header configured in one place and honoured in another is the worst outcome available: a green local run reads as proof. The contract now has an executable conformance fixture — this PRD covers what it does not yet cover, and what the same configuration surface should become for customers whose APIs authenticate differently from ours.

1. Summary

Shipped (uncommitted)
7-layer header contract
Implemented in all four executors, with a 10-case parity fixture that is byte-identical in three repos and green in every executor.
Immediate risk
12 fixes, 3 of them P0
Multi-suite cycle runs ship no contract at all; the MCP fixes exist only in source; path params resolve differently in the UI and the MCPs.
Product opportunity
One schema, two consumers
The same contract that configures test requests can configure tenant runtime auth — so what QA tests is literally what the gateway enforces.
Headline judgement on the security question. A tenant-defined required header is a valid control only when the header is injected from a different trust domain than the API key (a tenant's proxy, WAF or backend). Shipped inside a browser or mobile client it protects nothing — both secrets leak together — and positioning it as "your data is safe if your key leaks" would be false in the most common leak scenario. The strong version of the same idea is HMAC request signing, for which the schema (computedHeaders) already exists on the test side and needs only a verifying counterpart in the gateway. Details in §6.

Authentication is offered between layer 6 and layer 7 and never overwrites an Authorization an earlier layer set. A dataset opts out entirely via "noAuth": true, "Authorization": null, or by expecting 401 while declaring no credential of its own. 403 is deliberately not inferred: a 403 case is normally authenticated-but-not-permitted, so stripping its credential produces a 401 and the test fails for the wrong reason.

2.3 Storage and transport

  • Local / repo: tests/config/test-config.json — authored by the developer or the coding LLM.
  • ProjexLight: test_environment_configs.custom_env_vars.headerContract, one reserved key in an otherwise free-form bag.
  • Cloud container: one env var, PROJEXLIGHT_HEADER_CONTRACT, in exactly the test-config.json shape. One variable rather than flattened API_HEADER_* vars, because flattening loses header-name casing and the computed layer signs the name verbatim.

2.4 Conformance

header-parity-fixture.json — 10 cases, byte-identical in all three repos — is run against each executor's own resolver. Every harness offers a token before applying the executor's opt-out rule; a harness that never offers one turns each "sends no Authorization" case into a pass that proves nothing, which is precisely how a real divergence survived its first review.

3. Fix now

Twelve items. P0 means the contract is not actually in force for some runs, so a green report is not evidence. Each names the file that has to change and what "done" looks like.

P0 FIX-01 Multi-suite cycle runs ship no header contract at all
server/src/services/testing/SecureTestCycleExecutionService.ts (~line 303)

The single-suite path builds container env with buildHeaderContractEnv() + plainCustomEnvVars() (test-suite-management.ts:1264, test-cycle-management.ts:200). This service builds its own env map and emits neither — no PROJEXLIGHT_HEADER_CONTRACT, no custom_env_vars, no API_HEADER_*. The same suite therefore sends different headers depending on how it was launched, and the multi-suite path is the one used for full regression.

Done when: a cycle run and a suite run of the same suite produce identical resolved headers, asserted by an integration test that reads the container env.
P0 FIX-02 The MCP auth fixes exist only in source
projex_test_mcp (Nuitka image), projex_dev_mcp/dist

Both MCPs run as compiled images in the cloud; editing .py changes nothing until scripts/build_full.sh --push republishes projexlight/projex-test-mcp and the dev MCP dist is rebuilt. Until then, cloud runs still inject a bootstrap token into every noAuth / 401 dataset that does not carry a literal "headers": {}.

Done when: both images carry dataset_suppresses_auth, and check_parity.py run inside each image reports 10/0.
P0 FIX-03 Path parameters resolve in the UI and not in either MCP
api_test_runner.py _substitute_path_params (~3045); api_tester.py (~3415); PathParameterEditor.tsx

The UI extracts and replaces three spellings — :param, {param} and {{param}}. Both MCPs match :param only, and the Test MCP's substitution returns early when the URL contains no :. MUST-22 explicitly tells authors to keep :id / {id} / <id> literal, so an OpenAPI-style definition passes in the UI and goes out of both MCPs carrying a literal {userId} — a 404 that reads as a broken endpoint. Multiple path params are otherwise fully supported everywhere.

Done when: all three spellings resolve in all four executors, with fixture cases for a two- and three-param URL.
P1 FIX-04 Test MCP wipes every header on a negative dataset; the others drop only the credential
api_test_runner.py, the _is_negative_test branch (~2221)

"headers": {} plus a 4xx expectation sets headers = {} — dropping x-api-version, Accept-Language and the environment's api-key along with the token. The other three executors keep configuration layers and remove only Authorization. Wiping content-negotiation headers on a negative case produces 415/400s that mask the assertion under test. This is a behaviour decision, not an obvious bug — it is called out rather than changed.

Done when: the decision is recorded, all four executors agree, and a fixture case pins it.
P1 FIX-05 Nothing can author the contract from the UI
client/src/modules/tenant — no writer for custom_env_vars.headerContract

headerContract is read by the resolver and written by no screen. Today a tenant or QA engineer must hand-write JSON into a database column. Needs an Environments editor covering defaultHeaders, providers[], testCredentials, computedHeaders and per-environment variables, with secret masking and a live "resolved headers for this endpoint, and the layer each came from" preview.

Done when: every layer is editable in the portal and the preview matches what the server resolver sends.
P1 FIX-06 The API Library panel silently applies three of seven layers
api-library/types.ts Environment has no custom_env_vars

The API Library environment object never loads the column the contract lives in, so its client-side send applies layers 2, 5 and 6 while the api-testing module applies all seven from the same data. The same endpoint gives two answers depending on which screen you opened, and only "Test via server" is complete. Fix by including custom_env_vars in the environments payload and routing the panel through the shared headerResolution.ts.

Done when: both UI surfaces resolve identically, or the panel's client-side send is removed in favour of the server path.
P1 FIX-07 MUST-70 is instructed but never enforced
projexlight_review_api_definitions — enforces MUST-38 only

The reviewer rejects {{static:}} in headers and nothing else header-related. A custom header pasted into thirty definitions, a secret literal in a header map, or requiresRole declared alongside an explicit Authorization all pass review. The last one is the documented cause of 403s that read as API permission bugs.

Done when: the reviewer flags (a) a header repeated across ≥3 definitions, (b) a secret-shaped literal in any header map, (c) requiresRole + Authorization on one definition.
P1 FIX-08 Auto-configuration scaffolds variables but never header layers
projex_dev_mcp/src/core/server.py ~229–450 (the {{var:}} auto-populator)

The populator already walks every definition and writes typed placeholder slots into global vs per-environment variables. It writes no defaultHeaders, providers[], testCredentials[].headers or computedHeaders — so the LLM must hand-author every layer from MUST-70 with nothing to catch it when it does not. The same pass can detect a header repeated across N definitions and scaffold it up a layer, values left as {{var:}} slots for a human to fill.

Done when: a project whose definitions share x-api-key gets a scaffolded defaultHeaders/providers[] entry plus the matching secret slot, and the definitions are rewritten to drop the duplicate.
P1 FIX-11 Authentication scheme is environment-wide, so one run cannot authenticate to two systems
apiLibraryRoutes.ts test-api (bearer / api_key / basic / oauth2); providers[] carry static headers only

A single test run that touches ProjexCloud and a customer's legacy system needs two different schemes at once. providers[] can match the legacy path but can only attach static headers, and the environment's apiAuthType applies to everything. See §4.

Done when: providers[].auth exists and a request matching a provider uses that provider's scheme instead of the environment default.
P1 FIX-12 Computed headers can only sign the raw body
headerContractResolver.ts applyComputedHeaders; the Python equivalents

over: 'raw_body' with HMAC-SHA1/256/512 covers GitHub- and Meta-style webhooks and nothing else. Most enterprise schemes sign a canonical string — method, path, date, content-hash — and require companion Date, X-Timestamp or X-Nonce headers to exist before signing. Without this the connector tests for those customers cannot be expressed at all. See §4.

Done when: over: 'canonical' with a template, plus auto-emitted timestamp/nonce headers, resolves identically in all four executors with fixture coverage.
P2 FIX-09 Verify the noAuth round trip end to end
api_orchestration_builder.py (carried as of this change) → api_library → UI dataset editor

The flag is now mapped into test_data_sets, but the append-datasets merge path and the UI's dataset editor have not been verified to preserve or expose it. A flag an author can set and no screen can see is a flag that silently stops being set.

Done when: a definition with noAuth survives publish → api_library → UI edit → re-save, and the dataset editor exposes it as a checkbox.
P2 FIX-10 The parity fixture covers headers only
parity/header-parity-fixture.json — 10 cases, all header-shaped

Path params (FIX-03), query params, and the auth schemes themselves (bearer / api_key / basic) are resolved by the same four executors with no conformance coverage. Every divergence found so far was in exactly this class.

Done when: the fixture is renamed to a request-contract fixture and covers path params, query params and each auth scheme.
P2 FIX-13 Audit secret masking across reports and logs
run logs, interactive report, env panel preview

The server test route logs header names and layers only, deliberately. The MCP run logs, the generated HTML report and any future resolved-header preview need the same treatment — testCredentials holds role tokens and computedHeaders holds signing secrets.

Done when: a grep of a full run's artefacts finds no configured secret value.

4. Supporting a customer's existing auth framework

The integration ask — "a customer needs different keys and values to call their legacy systems, and to build and test those APIs on ProjexCloud" — is mostly satisfied by the layer model already. What is missing is that a layer can carry headers but not a scheme.

HMAC over a canonical string (SigV4, Azure SharedKey, WSSE)NoFIX-12 — over: 'canonical' + timestamp/nonce

The design principle worth keeping. A customer integration is described by where a rule applies (providers[].match) and what it contributes (headers, scheme, signature). Adding auth and a canonical signer to the provider block covers the long tail without a second configuration system — and it keeps every executor able to reproduce the request.

5. LLM auto-configuration of test-config

Yes — the LLM generates the configuration; the platform instructs rather than emits it. That distinction matters for what to build next.

Instructed (deterministic delivery)
Rules the agent receives every task
MUST-70 (layer model, secrets in environment variables, never requiresRole + Authorization, signatures are computedHeaders), MUST-38 (no {{static:}} in headers), MUST-35/46 (shared values as {{var:}}, secrets never global), plus the worked examples in the DEV_MCP.md reference section. The agent then authors the JSON.
Generated (deterministic code)
Only the {{var:}} slots
The auto-populator scans definitions, skips producible names (those must become {{cache:}}), and writes typed placeholder entries split into global vs per-environment variables with a _variable_meta guidance block. Header layers are not scaffolded and MUST-70 has no reviewer check — FIX-07 and FIX-08.

The gap this leaves is predictable: instruction-only compliance degrades silently. The agent authors headers correctly when the rule is fresh in context and pastes them per-definition when it is not, and nothing fails. Closing it means the same two mechanisms that already work for variables — scaffold and review — applied to headers.

6. Tenant custom headers as a security layer

6.1 The proposal

A tenant configures, in the tenant portal, an additional header its ProjexCloud SDK APIs must carry — so that an exposed API key alone cannot reach the tenant's data.

6.2 Honest assessment

A required custom header is a second static shared secret travelling over the same channel as the first. Its value depends entirely on where it is injected.

Where it is real
Different trust domains
The tenant's edge injects it — WAF, reverse proxy, their own backend — while the API key lives in the app. A key stolen from the app is then useless from anywhere else. This is the Authenticated Origin Pull pattern and it genuinely shrinks blast radius. It also decouples rotation: the header can be rotated without reissuing keys across integrations, and rejections make a clean pre-business-logic audit signal.
Where it is not
Same package as the key
In a browser app it is visible in the network tab and forces a CORS preflight; in a mobile binary it is extractable. Both secrets leak together, so the control does not address the threat it is pitched against. And it offers no replay protection at all — a static header is copyable along with the request it sits in.
The failure mode to avoid is not technical. A control that reads as protection while providing none is worse than no control, because teams skip the ones that work. If this ships, its documentation must state the injection requirement as a condition, not a recommendation.

6.4 Recommendation

  • Ship the header configuration as an integration feature — per-tenant, per-environment, per-provider header maps with encrypted values. It is needed for legacy connectivity regardless and carries low risk.
  • Put the security story on signing, not on the static header. Same configuration surface, same test contract, and it survives the leak the header does not.
  • Use one schema for both the tenant's runtime configuration and the QA test configuration. Then the parity fixture is covering production behaviour, and "we tested it" and "the gateway enforces it" become the same statement.

7. Guardrails — non-negotiable if this ships

Critical
Reserved-name denylist
A tenant-supplied header map must never set or override Authorization, X-Tenant-Id, X-App-Id, cookies, or X-Forwarded-*. Without this, a header-config feature becomes a tenant-identity spoofing surface — strictly worse than not shipping it.
Critical
Per-tenant scope on every write
Configuration and rotation endpoints must verify the credential belongs to the calling tenant. The cross-tenant rotate hole found in the app-credentials work is the same bug class waiting to recur here.
Required
Secrets handled as secrets
Envelope encryption at rest, masked in logs, reports and previews, scoped per environment, never in a global block (MUST-46). Constant-time comparison on verification.
Required
Per-app enforcement mode + audit
off | report | enforce, mirroring AUTH_GATE_MODE, so a tenant can roll out without locking themselves out. Emit an audit event on every rejection — that event is the leak signal.

9. Open decisions

  1. FIX-04: should a negative dataset's "headers": {} drop every header or only the credential? Four executors currently disagree; the fixture cannot pin it until this is decided.
  2. Schema unification: does the tenant runtime configuration adopt the test-config.json shape, or does the test side adopt a new runtime shape? Sharing one is the point; which direction is a migration question.
  3. Enforcement default: should a newly configured required header default to report for a fixed window before enforce?
  4. Where the LLM's authority ends: may the auto-populator rewrite existing definitions to remove a header it has just promoted to a layer, or only propose the change?
