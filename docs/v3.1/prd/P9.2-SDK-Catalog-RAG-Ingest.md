## 1 · TL;DR

P9 made the SDK catalog *describable* (manifests), *findable* (registry + embeddings), and *callable by AI* (MCP). But the first tenant-facing planner at `/build` took the cheapest shortcut on top of it — it loaded **all ~90 SDK manifests into a single LLM prompt** and trusted the model to pick. In production that returned **only ~3 SDKs**, dropped the identity/AIM foundation the user never explicitly asked for, cost ~18k tokens per plan, and rode entirely on whichever frontier model was wired in.

P9.2 fixes this and closes two manifest gaps:

1. **RAG catalog store** — the registry evolves from a build-time file artifact into an **auto-populated Postgres + pgvector store** (`catalog.*`, 384-dim bge-small, HNSW), auto-migrated on boot and incrementally synced from manifests.
2. **Planner v2** — `/build` becomes **retrieve-then-compose**: embed intent locally → vector top-K → **inject the foundation/AIM tier** + **dependency closure** → compose from candidates only. Auth/AIM is guaranteed to surface; tokens drop ~5×; the generation provider is swappable behind an adapter while retrieval stays on a local model.
3. **Manifest contracts** — endpoints gain **request/response payload schemas + `auth_scopes`** and an **`endpoint.kind`** classifier (`ingest|bulk|query|mutation|webhook`).
4. **Ingest front door** — a first-class **`sdk-ingest`** batch endpoint (`POST /api/ingest/:entity/batch`) plus MCP tools (`get_endpoint`, `get_ingest_targets`) so ETL agents discover *where to push data and with what payload*.

**Provider-independence principle:** retrieval embeddings run on the local `bge-small-en-v1.5` model and live in Postgres; the generation LLM only ever ranks/explains the already-retrieved candidates. A generation-provider change can never alter which SDKs are discovered — only the prose.

## 2 · Why this phase now

The P9 GA planner shipped behind `/build`. Field use surfaced three concrete failures, captured from a live "financial accounting system" prompt:

| Problem | Cause | Impact |
|---|---|---|
| **"Always 3 SDKs"** | No retrieval/ranking/minimum; flat 90-SDK dump to a small model | The identity/AIM foundation silently dropped into "you'll need to build" — tenants risked rebuilding auth |
| **~18k tokens/plan** | Whole catalog shipped on every request | Cost scales with SDK count, not query; grows on every new SDK |
| **Provider-coupled discovery** | Discovery quality rode on the frontier model | A provider deprecation/model swap silently changed results |

These are not features to defer — they undermine trust in the headline P9 builder experience. P9.2 is the corrective layer, built on infrastructure P9 already shipped (manifests, the `sdk-registry` scanner + embedder, `sdk-knowledge-rag`'s `VectorBackend` interface, `migration-runner`, the `global-catalog` pool).

## 4 · User stories

### As a **Tenant Employee / Developer** (builder)
- **US-92-1:** When I describe any app, the planner returns the *relevant* SDK set (typically 8–12), not a random 3 — and **always includes the identity/AIM foundation** (login, personas, tenancy, permissions) so I don't rebuild auth.
- **US-92-2:** The plan splits **recommended SDKs** from **custom UI work** (e.g. "login page wired to `/api/auth/login`", "admin page calling `rebac.expandPermissions`"), because the platform ships the auth SDKs but not the pages.
- **US-92-3:** The planner keeps working — and keeps producing the same SDK set — even if the platform swaps the generation LLM provider.

### As an **AI Coding Agent / Custom Agent** (Claude Code, Cursor, ETL bot)
- **US-92-4:** I can call `get_endpoint(sdk, path)` to get the exact method/path/**payload schema/auth scope** before calling an API, so I don't guess the body or reimplement an existing endpoint.
- **US-92-5:** I can call `get_ingest_targets(entity)` to discover **where external data is imported and with what payload**, so my ETL job pushes records to the right endpoint without hardcoding.

### As a **Platform Engineer** (internal)
- **US-92-6:** The catalog is an auto-migrated, auto-synced Postgres store (not a hand-managed file), so multiple hosted instances share one fresh source of truth and reload on a version bump.
- **US-92-7:** SDK owners can declare endpoint payload contracts (`request_schema`/`response_schema`/`auth_scopes`) in the manifest, generated from existing Zod/TS types.

## 5 · Functional requirements

### 5.1 · `@projexlight/sdk-catalog-index` (Epic A)

**Purpose:** the global SDK catalog RAG store — source of truth for the build planner + registry MCP retrieval.

- **FR-CAT-1:** Ships `src/db/migrations/001_init_catalog.sql` creating the `catalog` schema in the **global-catalog pool**: `catalog.sdk`, `catalog.endpoint` (with `kind`/`request_schema`/`response_schema`/`auth_scopes`), `catalog.embedding` (`vector(384)` + HNSW `vector_cosine_ops`), `catalog.sync_state`. **Auto-applied on boot** by `migration-runner` — no manual SQL. The 384-dim bge-small space is kept separate from the 1536-dim `agent-runtime` template. *(TK-3457/3458)*
- **FR-CAT-2:** `syncCatalog()` reuses the `sdk-registry` scanner to walk every `sdk-capability.json`, computes a `sha256` content hash per manifest, and **upserts only changed SDKs/endpoints/scenarios** (idempotent, incremental). *(TK-3460)*
- **FR-CAT-3:** For changed rows, builds natural-language cards (per sdk/endpoint/scenario/ingest) and embeds them with the shared **bge-small-en-v1.5** in-process model → `catalog.embedding`. *(TK-3461)*
- **FR-CAT-4:** Shared, provider-independent embedder (`embed`/`embedAll`/`getEmbedder`) used by both sync and query; model id + dim pinned; never calls an external embedding API. *(TK-3463)*
- **FR-CAT-5:** Read API: `searchCatalog(vec, topK, {kind?})` (HNSW cosine, best-score-per-SDK), `getEndpoint(sdk, path)`, `getIngestTargets(entity?)`, `getSyncVersion()`, `bumpSyncVersion()`.
- **FR-CAT-6:** Hot-index loaders `loadCatalogSnapshot()` / `reloadIfChanged(knownVersion)` for an in-memory MCP index refreshed on `catalog.sync_state` version bump (LISTEN-ready). *(TK-3478)*

**Pool placement:** Global Catalog. **SKUs:** `catalog.search` (metered). **Events:** `catalog.synced.v1`.

### 5.2 · `@projexlight/sdk-knowledge-rag` — `PgvectorBackend` (Epic A)

- **FR-CAT-7:** Production `PgvectorBackend implements VectorBackend` (upsert/query/drop) over per-tenant `vector_<namespace>.embedding`, replacing `InMemoryVectorBackend`; sanitized schema identifier; HNSW cosine query. Wired via `setVectorBackend()`. *(TK-3459/3462)*

### 5.3 · `@projexlight/sdk-capability` — contract enrichment (Epic B)

- **FR-CON-1:** `ManifestEndpoint` gains optional `kind: 'ingest'|'bulk'|'query'|'mutation'|'webhook'` (defaults `query`), validated by an `ENDPOINT_KINDS` enum. *(TK-3466)*
- **FR-CON-2:** `ManifestEndpoint` gains optional `request_schema` / `response_schema` (JSON Schema objects) + `auth_scopes` (string[]); validator type-checks them; **backward-compatible** (older manifests still pass). *(TK-3465)*
- **FR-CON-3:** Dependency-free `zodToJsonSchema(schema)` introspects Zod `_def` at runtime (object/string/number/boolean/array/enum/optional/nullable/default) so a build step can derive endpoint schemas from each SDK's existing Zod/TS types. *(TK-3464)*
- **FR-CON-4:** Data-entry endpoints tagged `kind: ingest` across manifests (pilot: `sdk-media` upload-url, `sdk-diagnostic-telemetry` crash, `sdk-evidence` capture); ingest cards embedded with `ref_kind='ingest'`. *(TK-3467)*

### 5.4 · `@projexlight/sdk-ingest` (Epic B)

- **FR-ING-1:** Exposes `POST /api/ingest/:entity/batch` with envelope `{ entity, mode: upsert|insert, idempotency_key, records[] }`; lands rows **idempotently** in `ingest.record` (unique on `entity, idempotency_key, external_id`); returns `{ imported, skipped, errors[] }`. *(TK-3468)*
- **FR-ING-2:** Records provenance via **sdk-lineage** and an append-only entry via **sdk-audit** through pluggable `setIngestHooks(...)` (best-effort; never blocks the import); the gateway wires the real implementations at boot. *(TK-3469)*
- **FR-ING-3:** Manifest declares the endpoint `kind: ingest` + `request_schema` + `auth_scopes: ['ingest:write']`, so it is discoverable via `get_ingest_targets`.

**Pool placement:** Tenant App Pool. **SKUs:** `ingest.batch` (metered, per record). **Events:** `ingest.batch.completed.v1`.

### 5.5 · Planner v2 — `apps/tenant-workspace` (Epic C)

- **FR-PLAN-1:** `/api/build/plan` is rewritten as a pipeline: load catalog → **retrieve top-K** (pluggable `Retriever`) → **inject foundation** → **expand dependencies** → **compose from candidates only**. The flat ~90-SDK dump is removed. *(TK-3470)*
- **FR-PLAN-2:** Retrieval is a stable interface with three backends selected by `BUILD_RETRIEVER` and chained by `FallbackRetriever` (`pgvector → embedding → lexical`): `LexicalRetriever` (zero-dep), `EmbeddingRetriever` (bge-small over the `sdk-registry` file index, **default**), `PgVectorRetriever` (the `catalog.embedding` store). *(TK-3470)*
- **FR-PLAN-3:** Candidates are hydrated with their endpoints (method/path/kind) before composing, so the plan can cite concrete APIs; only candidates are hydrated, not the full catalog. *(TK-3471)*
- **FR-PLAN-4:** **Foundation-tier injection** — SDKs tagged `tier='foundation'` (`sdk-identity`, `sdk-persona`/AIM, `sdk-tenant`, `sdk-rebac`) are added regardless of semantic score and deduped, unless the intent is explicitly single-user/anonymous. *(TK-3472)*
- **FR-PLAN-5:** **Dependency closure** — walk the manifest `consumes`→`provides` event graph to pull foundation prerequisites of selected SDKs, each with a "why included" rationale. *(TK-3473)*
- **FR-PLAN-6:** Generation behind a `GenerationProvider` adapter (OpenAI/Anthropic, swappable via `BUILD_PLAN_PROVIDER`); retrieval unaffected by the choice. *(TK-3474)*
- **FR-PLAN-7:** `/build` UI renders foundation/prerequisite badges, a "how these were found" discovery panel, and splits recommended SDKs from custom UI work. *(TK-3475)*

### 5.6 · Agent discovery surface (Epic D)

- **FR-DISC-1:** `registry-mcp-local` adds `projex_registry_get_endpoint(sdk, path)` → `{method, path, kind, request_schema, response_schema, auth_scopes}` and `projex_registry_get_ingest_targets(entity?)` → ingest/bulk endpoints + payload + scopes. *(TK-3476)*
- **FR-DISC-2:** Hosted `services/registry-mcp` re-exports `READ_TOOLS`/`dispatchTool` from `registry-mcp-local`, so both tools appear in the hosted surface after a rebuild. *(TK-3477)*
- **FR-DISC-3:** Documented + verified ETL agent loop (`../etl-agent-discovery-example.md`): search ingest endpoints → `get_ingest_targets` → read `request_schema` → map columns → POST batch → watch ingest/lineage events. *(TK-3479)*

## 6 · Non-functional requirements

| Dimension | Target / Result |
|---|---|
| Planner prompt size | ~18k tokens (flat dump) → **~3–4k** (top-K candidates) — ~5× reduction |
| Planner recall | ~3 SDKs → **8–12 relevant** + guaranteed foundation tier |
| Retrieval embedding | Local `bge-small-en-v1.5` (in-process, ONNX); ~0.6s warm load; query embed ~5ms |
| Vector query (pg) | HNSW cosine over `catalog.embedding`; off the agent hot path (in-memory index serves search) |
| Catalog sync | Incremental by content hash; full first sync ~21s for 98 SDKs; re-sync touches only changed |
| Provider independence | Retrieval never calls an external API; generation provider swappable with zero effect on which SDKs surface |
| Migration | `catalog.*` auto-created on boot, idempotent (`IF NOT EXISTS`), SHA-tracked forward-only |
| Ingest idempotency | Re-running a batch with the same `idempotency_key` upserts, never duplicates |

## 10 · Decisions

- **D-92-1:** **Catalog is global, not per-tenant.** SDK manifests are identical for every tenant → `catalog.*` lives in the `global-catalog` pool, separate from per-tenant `rag.*` corpus.
- **D-92-2:** **Hybrid store, not vectors-only.** Embed a natural-language *card* per sdk/endpoint/scenario for discovery; fetch the **exact** JSON Schema relationally by `(sdk, path)` for correctness. Agents never reconstruct payloads from fuzzy hits.
- **D-92-3:** **Separate the two model jobs.** Retrieval = local bge-small (stable contract, 384-dim, pinned). Generation = swappable LLM over already-retrieved candidates. Provider change never alters discovery.
- **D-92-4:** **Foundation tier is injected, not retrieved.** Semantic search alone under-covers implicit cross-cutting concerns (auth), so `tier='foundation'` SDKs are added deterministically + a `consumes`/event-graph closure pulls prerequisites.
- **D-92-5:** **Migration always auto; data sync opt-in.** Tables auto-migrate on every boot; embedding population is gated behind `CATALOG_SYNC_ON_BOOT` to avoid per-instance startup cost.
- **D-92-6:** **Ingest is a first-class front door.** Connectors do event-driven *sync*, not bulk import; `sdk-ingest` provides the idempotent, lineage+audit-tracked batch path connectors never offered.
