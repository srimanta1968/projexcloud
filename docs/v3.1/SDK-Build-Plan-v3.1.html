SDK Build Sequence — Complete Wave-by-Wave Roadmap

A wave-by-wave plan for building the 57 SDK packages + ~10 connector packages + 11 HDK modules + 6 foundation packages (~84 total) that span projex_common/packages/ and projex_common/native/, organized into 8 dependency-driven phases with hard exit gates (see §0A). v3.1 integrates v2's full SDK estate with v3's four new SDKs (sdk-pool-router · sdk-rebac · sdk-persona · sdk-engagement), five modifications, and v3.1 ten new SDKs: two for metering/billing (sdk-meter · sdk-billing — every call gated and priced per method per tenant per app); six for hierarchy + functional gaps (sdk-api-keys · sdk-data-rights · sdk-webhook · sdk-approval · sdk-tenant-lifecycle · sdk-lineage); two from Analyze.txt mandates (sdk-identity-resolver — centralized layer resolution; sdk-semantic — the Enterprise Semantic Model Layer, "the largest architectural gap"). Plus extensions to sdk-tenant (reseller + sub-tenant + recursive BU + geo + roles + fiscal), sdk-identity (SAML/SCIM federation + tenant impersonation), sdk-audit (customer-read API + event taxonomy + retention/compaction), sdk-policy (Identity Query Language), sdk-rebac (computational safeguards), sdk-agent-runtime (agent identity + memory isolation), and sdk-pool-router (federation hooks for the 1000+ pool world). Every wave names the SDKs, their dependencies, what they unlock, and why this order and not another.

0A · Phase Plan — Dependency-Driven Delivery v3.1

The wave-by-wave plan that follows (§1–§8) is the SDK-level schedule. This section is the doctrinal layer above it — the 8 phases that define what must be true before the next layer of code can start. The phases are not aspirational; they are dependency-derived. Every phase has a hard exit gate, and CI enforces that no PR in Phase N can import an unstable Phase N-1 SDK.

Why this section exists. Two independent architectural reviews (../../Analyze.txt · ../../Analyze2.txt) converged on the same critique: at hyperscale, the v3.1 estate's dependency cycles will collapse under their own weight unless the ordering is enforced at the planning layer, not discovered at integration time. The 8 phases below are the answer. The 12 numbered gaps (G1–G12) referenced throughout are the items that must be closed by specific phases to prevent later collapse.

0A.5 · The five no-leak rules

Rule 1
Phase exit gate is binary
A phase is either fully exited (all gate items true) or not. There's no "Phase 2 mostly done; start Phase 3" — every Phase 3 PR is blocked at CI by an unstable upstream.
Rule 2
Doctrines from P1 are CI-lint-enforced from week 1
Opinionated Constraints + Polyglot Persistence + Pool Placement + Event Type Registry have no opt-out for later phases. They are the substrate, not a recommendation.
Rule 3 · G4
Identity Projection MUST land in P2
If a P3 SDK starts calling resolver before projection exists, resolver becomes the bottleneck and you can't retrofit projection without re-instrumenting P3 SDKs. Single biggest dependency violation risk.
Rule 4 · G6
Conflict Resolution Model MUST land before HDK camera/map (P4)
Every HDK module after foundations does offline-write. Without the model, conflicts accumulate in production. Cannot be retrofitted from collected bad data.
Rule 5 · G7
Agent Isolation Runtime MUST land in P6A before any P6B agent
A single Phase 6B agent using P6A's runtime without isolation primitives leaks one tenant's prompt context into another's. The leak is catastrophic and irreversible.
Bottom line. The 8 phases, 8 exit gates, 12 gap closures, and 5 no-leak rules are the contract that makes the 56-SDK estate deliverable without collapse. Sections §1–§8 below are the per-SDK detail under this phase plan.

1 · Overview

The platform's SDK estate spans five classes: (a) foundation packages (contracts · telemetry · branding · design-system · config · i18n); (b) backend SDKs that wrap horizontal services (identity, vault, profile, payment, …); (c) the AIM SDKs introduced in v3 (pool-router · persona · engagement · rebac); (d) native HDK modules that bridge device capabilities into React Native; v3.1 (e) the metering & billing SDKs (sdk-meter · sdk-billing) that gate, meter, and invoice every API call against per-method pricing. They must be built in dependency order.

Goal
Ship in dependency order
No SDK begins coding until the contracts it depends on are merged. Public APIs of upstream SDKs land in @projexlight/contracts first; the implementation follows.
Constraint
Compliance & pool routing are structural
Vault, Audit, Consent, Policy, and Pool Router land before any SDK that touches data. Retrofitting compliance or routing after data has spread is the largest avoidable cost.
Mechanic
Contract-first, then code
Every wave begins with a contract PR registering the wave's new types/events. Implementations land afterward. CI runs cross-consumer contract tests on every change.

2 · Why This Exact Order — Build Rules

The sequence is not aesthetic. Each rule below is a refactor we are choosing not to do, valued in weeks of avoided rework or in compliance liability avoided.

Rule 1
contracts first — always
Without typed primitives (canonical IDs, scope hierarchy, envelope, six identity types, pool-routing types), every later SDK ships with its own copy. Cost of skipping: 6–10 weeks of cleanup per type drift.
Rule 2
Vault + KMS before any PII handler
Multi-level encryption (root · pool · tenant · person · device · org · encounter). Ship Identity / Profile without per-person keys and you cannot retrofit cryptographic-shred erasure. Cost: non-recoverable compliance debt + multi-month re-encryption project.
Rule 3
Audit before MDM
Every key shred, MDM merge, consent grant, ABAC/ReBAC decision must be immutably logged. Build MDM before Audit and pre-Audit history is non-attestable.
Rule 4 v3
Pool Router before any data-touching SDK
Every SDK from W2 onwards routes through Pool Router. Build later and every SDK ships with its own routing shim that must be ripped out. Cost: 6+ weeks of routing refactor across 30+ SDKs.
Rule 5
Tenant before Identity
JWTs carry app_id · bu_id · tenant_id · org_id + (v3) pool indices. Mint tokens without the full scope and every later policy decision guesses tenancy.
Rule 6
Identity before Consent
Consent receipts are keyed by person_id. Recording consent against a non-canonical subject orphans the receipts.
Rule 7
Consent + Policy + ReBAC before Profile/Persona
Every read of personal data must clear ABAC + Consent + (when relationship-applicable) ReBAC. Build Profile/Persona first and every read is unauthorized-by-design.
Rule 8 v3
Persona before Engagement / CRM
Encounters and Relationships reference Personas. CRM contacts are keyed by Persona, not raw person_id. Building Engagement first means inventing a temporary identity model that must be replaced.
Rule 9
Profile/Persona before Notification & Payment
Notification reads the notification routing band of App Identity; Payment touches the Secure-Data band on Master Person. Build them first and you duplicate PII across services.
Rule 10
Geo (address_id) before Property / Asset / Encounter-location
Without canonical address resolution, every vertical produces duplicates from every feed.
Rule 11
AI Gateway before Agent Runtime
Agents call models. Without a gateway, N agents each hold their own provider keys, PII redaction, budget code.
Rule 12
Taxonomy before Parsing
Parsing selects extraction schemas at runtime from Taxonomy. Without Taxonomy, schemas hard-code into the engine.
Rule 13
Vault + Audit before Evidence
Evidence chain requires immutable storage and audit. Build Evidence first and evidence is mutable — defeating its legal purpose.
Rule 14
HDK runs parallel from Wave 4 — never earlier
HDK consumes backend SDKs (identity → idp, vault → idp, policy → permissions, geo → map). Starting earlier means writing native code against changing TS types.
Rule 15 v3
Engagement before CRM / SR / Event
CRM contacts have engagement-stage; SR tickets are engagement-of-kind ticket; Events are engagement-of-kind session. Building these first invents redundant primitives.
Rule 16 v3.1
Meter before any billable SDK call
Pay-as-you-use is structural. Without sdk-meter emitting from operation #1, usage history is unreconstructible, per-method pricing cannot be validated against real traffic, and customer bills cannot be audit-verified. Build later and every W2+ SDK ships without metering and must be re-instrumented. Cost: 8–12 weeks across 30+ SDKs + multi-month gap of unbillable production traffic.
Anti-pattern radar. If a wave's owner says "we can start now and figure out the dependency later" — the dependency they want to skip is almost always Vault, Consent, Pool Router, or Persona, and the result is non-recoverable.

8 · Risks & Anti-patterns

Risk · High
"Just stub it" on Vault or Pool Router
Pressure to ship Identity before Vault is real, or to ship W2+ SDKs without going through Pool Router. Stubbing means real PII flows into unencrypted columns "temporarily" and SDKs accumulate their own routing shims. Mitigation: CI fails any PR that imports sdk-profile while sdk-vault is not at v1.0; CI fails any SDK that opens a Postgres connection without withTenant(...).
Risk · High
Skipping Audit while "compliance reviews schemas"
Audit deprioritized because it doesn't have a user-visible surface. But it is the proof every wave's gate depends on. Mitigation: Audit exit gate (chain-tamper alert) non-negotiable.
Risk · High
Persona collapsed back into a single profile row
A vertical insists "we only need one profile per user". Works for that vertical, breaks for healthcare/eCommerce. Mitigation: Persona is mandatory; Profile SDK no longer exposes a per-user row API — only per-App-Identity.
Risk · Medium
Vertical teams forking the canonical entities
Verticals may try to create property_owner_name columns "for now". Breaks erasure and consent. Mitigation: lint rule forbids personal-name / address-string / device-serial columns on any non-MDM table. Also bans visit/order/session tables outside sdk-engagement.
Risk · Medium
HDK starts too early
Mobile engineers idle waiting for backend — temptation to start HDK in week 4. Result: TypeScript types churn, native code rewritten. Mitigation: HDK teams work on tooling (RN bridge generator, parity-CI matrix, native module skeletons) until Week 22.
Risk · Medium
AI Gateway long-pole compresses W6
6-week Gateway build blocks 6 downstream AI SDKs. Mitigation: Gateway gets the strongest team and starts the moment W5 ships; Taxonomy runs in parallel since it doesn't depend on Gateway.
Risk · Medium
Pool capacity surprise
High-growth tenant fills a shared pool quickly, slowing co-tenants. Mitigation: Pool Capacity Steward dashboard; auto-quarantine + migration when utilization > 90%.
Risk · Medium
ReBAC graph grows unbounded
10-year-old patient-doctor relationship clutters the graph. Mitigation: Relationship lifecycle includes auto-expiry; healthcare PCP relationships re-attest annually.
Risk · Medium
Encounter scope creep
Verticals invent their own "Session" / "Visit" / "Order" entity instead of using Encounter. Mitigation: lint ban + Engagement is the only sanctioned home.
Risk · Low
Contract drift across SDKs
Independent SDK teams may add fields outside contracts. Mitigation: service-side schema validators reject events whose event_type is not registered in @projexlight/contracts; CI runs cross-consumer tests.
Risk · Low
Promotion pressure before Rule of Three
A vertical pushes to promote a domain SDK to Common too early. Mitigation: Common-Platform Working Group enforces Rule of Three as a hard gate.
Risk · Low
Documentation lag
SDK docs trail code by 3+ weeks; verticals integrate against the wrong contract. Mitigation: docs ship in the same PR as the SDK; release-cadence enforces a docs check.
Risk · High v3.1
Meter gate adds latency to every call
A 2ms gate on hot paths can dominate response time. Mitigation: admission check is a single in-process LRU lookup over a Redis-warmed quota state; CI fails any SDK whose p99 latency regresses > 3ms with meter enabled vs. disabled; emission is fire-and-forget to a local ring buffer flushed off the request path.
Risk · High v3.1
Pricing catalog drift breaks invoices
Sales/finance edits rates; a rate gets removed while an SDK method still references the SKU; that month's invoice has unpriced line items. Mitigation: SKU schema lives in contracts (typed; CI catches dangling refs); rates live in Postgres with a constraint that every active SKU has a rate row; orphan-SKU lint runs on every catalog edit; reprice-dry-run is mandatory before applying a catalog version to active tenants.
Risk · Medium v3.1
Hard cap denies legitimate traffic on day one
Enforcing caps before catalog is calibrated against real traffic causes outages. Mitigation: W1 ships emit-only mode (gate never denies; events flow). Soft caps (WARN headers) turn on in W4. Hard caps (DENY) only after one billing cycle of real data and tenant opt-in.
Risk · Medium v3.1
Usage event loss = revenue loss
Dropping events under Kafka backpressure means undercounting customers — direct revenue impact. Mitigation: at-least-once delivery with idempotent event_id dedup at the rollup worker; per-SDK ring-buffer with disk overflow if Kafka unavailable; reconciliation job compares raw event count to rollup totals nightly; chain-break alerts on missing days.
Risk · Low v3.1
Customer dispute without verifiable trail
"Why did my bill jump 5×?" — without a transparent trail, customers churn. Mitigation: hash-chained usage ledger per (tenant, day) linked into Audit; customer can hit /billing/verify?day=... and re-derive the day's total; /billing/live dashboard shows accruing cost < 60s after each call so surprises don't compound silently for weeks.
Risk · High v3.1
Identity resolver becomes a bottleneck
Every authenticated call routes through resolveIdentityContext() — if it's slow or fails, the whole platform stalls. Mitigation: p99 ≤ 1ms warm enforced in CI; warm-cache hit rate > 99%; cold-path fallback returns minimal context (L1+L2+L3) within 5ms; circuit breaker bypasses resolver and rejects request rather than hanging. Lint forbids any non-resolver SDK from reading layer attributes directly.
Risk · High v3.1
Semantic Domain Layer over-fits to vertical 1
The first ontology built (likely Healthcare) bakes in assumptions that fight every subsequent vertical. Same risk as building "common" abstractions from one example. Mitigation: Rule of Three applies to ontology promotion — a SemanticObject type lands in contracts only when a third vertical needs it. Vertical-specific concepts stay in vertical ontologies. Cross-vertical concepts (Person, Address, Money, Document) are introduced first as the universal core.
Risk · Medium v3.1
Agent memory leakage across tenants
A single prompt-engineering mistake or vector-store misconfiguration leaks Tenant A's data into Tenant B's agent context. Catastrophic compliance failure. Mitigation: hard memory partitions per tenant in the vector store layer (not just logical filters — physical namespaces); CI runs cross-tenant prompt-leakage tests on every agent change; any leakage halts release.
Risk · Medium v3.1
DSAR fan-out misses data
Right-to-erasure must touch every pool holding a person's data. If the inventory is wrong, "erased" data persists somewhere and the certificate of destruction is false — regulator-grade exposure. Mitigation: person_pool_residency registry written on every first-touch by any data-bearing SDK; weekly reconciliation job compares registry against actual data presence across pools; DSAR completion requires reconciliation green.
