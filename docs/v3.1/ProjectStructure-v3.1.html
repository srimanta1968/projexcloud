Repos · SDKs · Databases · Portals — How the Project Is Organized

This document is the canonical source of truth for: which repositories exist, what each contains, how SDKs are structured, how databases are organized, what admin and end-user surfaces ProjexCloud ships, and how tenant developers build their own apps on top. Every decision below is committed to the v3.1 design and matches the SDK Build Plan's phase model.

Scope · platform repo · vertical repos · customer repos · 5 surface types
The five decisions this doc commits to. (1) Multi-repo at the org boundary, monorepo within each org: one platform monorepo + one repo per vertical + customer-owned repos for custom apps. (2) One typed SDK template followed by all 55 SDKs — same directory shape, same code-gen, same release cadence. (3) Per-service per-pool schema isolation in shared Postgres clusters (one schema per SDK, RLS per tenant) — semantically "database per service" without the operational explosion. (4) Three platform-owned portals — ProjexCloud Admin (internal), Tenant Admin (per-tenant), Consolidated Tenant Workspace (the launcher). (5) Private npm registry for SDK distribution to vertical teams and tenant developers; same gated/metered/audited consumption as internal code.

1 · Overview — Why this doc exists

The v3.1 architecture commits to 55 SDKs + 11 HDK modules + 6 foundation packages across 8 dependency-driven phases, plus a multi-tenant platform that sells to enterprise customers who themselves build apps on top. Without a single canonical answer to "where does the code live, how is it shipped, and what surfaces does the platform expose," every team will invent its own answer and the platform will fragment.

This document fixes the answers. It is the "how do I navigate the project" guide for new hires, vertical owners, customer developers, and platform operators.

Source of truth
Every repo is named, every surface is placed
If a piece of code or a deployed surface isn't in this doc, it shouldn't exist. New artifacts require a PR to this doc first.
Built-in scale
Designed for 1 platform + N verticals + N customers
The structure assumes ProjexCloud will host its own verticals AND host customer-built custom apps. Both have first-class places.
CI-enforced
The Opinionated Constraints (Arch §3A) apply here too
No alternative repo topologies, no forks of the SDK template, no per-vertical Kafka or per-team Postgres. The platform owns the substrate.

3.1 · The three repo categories

Category 1
Platform monorepo
projex-platform/ (also addressable as projex_common/ per the existing README). One repo. Holds: contracts, all 55 SDKs, all 11 HDK modules, foundation packages, the 3 platform-owned portals, services, infra, internal tooling. pnpm + turbo workspace. Owned by the ProjexCloud platform team.
Category 2
Vertical repos (one per vertical)
projex-vertical-{healthcare,realty,seva,fieldops,oneestate,music,bidwork,leadpulse,…}/. One repo per vertical. Holds the vertical product's frontend + backend + vertical-specific domain types. Consumes @projexlight/sdk-* from the private registry. Owned by each vertical's product team.
Category 3
Tenant custom app repos
Customer-owned, outside ProjexCloud's GitHub org entirely. ProjexCloud has zero source-code access. Customer's developers install @projexlight/sdk-* from the registry (with their per-tenant token) and build whatever they want. Their app registers in the Tenant Workspace via Tenant Admin.

3.2 · Why this split (and not a single monorepo for everything)

ForceConclusion
Atomic contract changes across all SDKsPushes toward monorepo for the platform → confirms platform stays as one monorepo.
Vertical teams need independent release cadence (Healthcare ships weekly, Seva ships monthly, both shouldn't be coupled to platform releases)Pushes toward separate vertical repos consuming a versioned platform → confirms verticals as separate repos.
Customer source code must never enter ProjexCloud's repo (legal, IP, security)Pushes toward customer-owned repos. Hard rule — customer apps cannot be in our monorepo even if convenient.
Atomic refactors across vertical appsSometimes useful, but rare — verticals share contracts (which are atomic via the platform monorepo) and rarely need cross-vertical refactors. The cost of breaking vertical independence is higher than the cost of occasional multi-repo PRs.
Search across the whole codebaseUse Sourcegraph or GitHub code search across orgs. Not a reason to monorepo everything.

3.3 · Early-stage workspace linking (sibling-folder pattern)

The existing projex_common/README.md states: "The verticals' workspaces are siblings of projex_common/ and link via the parent pnpm workspace (or via a published private registry once we promote artifacts to packages)." v3.1 confirms this as the early-stage pattern:

  • Until contracts v1.0 ships (end of Phase 1): verticals live as sibling folders next to projex-platform/ and link via parent pnpm workspace. Fast iteration; breaking contract changes ripple immediately.
  • After contracts v1.0 ships: verticals migrate to their own repos and consume @projexlight/contracts + @projexlight/sdk-* from the private registry. Releases become semver-gated.
  • Tenant custom apps consume from the registry from day one — never sibling-folder.

4.1 · Top-level conventions

  • Everything publishable lives in packages/. Internal-only services live in services/. Native modules live in native/. Apps (portals) in apps/.
  • Package names use the @projexlight/ scope: @projexlight/sdk-identity, @projexlight/contracts, @projexlight/design-system.
  • Workspace dependencies use workspace:* in package.json — pnpm resolves to the in-tree version. CI rejects PRs that import a sibling-package's workspace:^0 (rule OC-10 from Architecture §3A).
  • Turbo pipelines define build · test · lint · publish with proper input/output caching. Builds are content-addressed.

6 · Database Strategy — Per-Service Per-Pool Schema Isolation

The v3.1 architecture commits to two principles that govern this:

  • P1 (Architecture §4): "Database per service. No cross-service joins. Services expose APIs and emit events; consumers project their own read models." — v3 refinement: "per service per pool."
  • §8B Polyglot Persistence: "Postgres is the right choice — but not for everything." Different workloads route to different storage engines.

Together, these answer the user's question — "separate database for each SDK?" — as follows.

6.1 · The OLTP answer: one schema per SDK within a shared Postgres cluster per pool

QuestionAnswer
Does each SDK get its own database server?No — that's operationally untenable. At 200 pools × 55 SDKs = 11,000 Postgres clusters. Unmanageable.
Does each SDK get its own logical database within a cluster?No — same operational issue at a smaller scale, plus connection-pool explosion.
What then?Each SDK gets its own Postgres schema within the pool's cluster. One pool = one Postgres cluster; within that cluster, schemas are named {sdk_name} (e.g., identity, persona, engagement, payment). RLS isolates tenants within each schema's tables. No cross-schema foreign keys — services communicate via events.

6.2 · The naming and isolation rules

-- Pool: app-healthcare-007 (a Postgres cluster)
-- Connection: app-healthcare-007.cluster.internal:5432
--
-- Schemas within the cluster:

CREATE SCHEMA identity;                  -- owned by sdk-identity
CREATE SCHEMA persona;                   -- owned by sdk-persona
CREATE SCHEMA engagement;                -- owned by sdk-engagement
CREATE SCHEMA payment;                   -- owned by sdk-payment
CREATE SCHEMA audit;                     -- owned by sdk-audit (per-pool chain)
CREATE SCHEMA workflow;                  -- owned by sdk-workflow
CREATE SCHEMA approval;                  -- owned by sdk-approval
-- … one per SDK that holds OLTP data in this pool

-- Each schema's tables get RLS:
CREATE TABLE persona.persona (
  persona_id text PRIMARY KEY,
  tenant_id  text NOT NULL,
  ...
);
ALTER TABLE persona.persona ENABLE ROW LEVEL SECURITY;
CREATE POLICY pol_tenant ON persona.persona
  USING (tenant_id = current_setting('app.tenant_id')::text);

-- Cross-schema foreign keys are FORBIDDEN at the SQL level via a CI lint:
--   ✗ ALTER TABLE engagement.encounter ADD CONSTRAINT fk_persona FOREIGN KEY ... REFERENCES persona.persona;
-- Instead:
--   ✓ engagement.encounter stores persona_id as a value; sdk-persona emits persona.created.v1;
--     sdk-engagement projects its own read model if it needs persona data inline.

-- Permissions: each SDK's service binary gets its own DB role with USAGE on its schema only.
CREATE ROLE svc_persona;
GRANT USAGE ON SCHEMA persona TO svc_persona;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA persona TO svc_persona;
-- svc_persona cannot read svc_payment's tables.

6.3 · Migrations

  • Each SDK owns its own db/migrations/ folder.
  • tools/migration-runner orchestrates: for each pool, run pending migrations per SDK schema, in SDK dependency order.
  • Migrations are idempotent and versioned. Rollback scripts required for schema-altering migrations.
  • The migration runner refuses to start a Phase N+1 SDK's migrations against a pool that hasn't completed Phase N migrations.

What this gives us. Each SDK is logically "its own database" — its own schema, its own RLS, its own permissions, its own migrations, no cross-schema joins. Operationally, we run ~200 Postgres clusters (one per pool) plus the polyglot stack — not 11,000. The architectural promise of "database per service" is preserved; the operational nightmare is avoided.

10.2 · The vertical's relationship to platform

11 · Surface 4 · Consolidated Tenant Workspace (the Launcher)

Tenant Workspace app.<tenant_slug>.projexcloud.com
The unified hub · Platform-team-owned · Lives in projex-platform/apps/tenant-workspace/
Audience
Every tenant employee / end user — patients, doctors, agents, contractors, devotees, customers — anyone who actually does work on the platform.
What it does
1) Aggregates surfaces. Shows the tenant all subscribed verticals (Healthcare · Realty · etc.) AND all registered custom apps in one navigation.
2) Shared shell. One nav bar, one notifications dropdown, one profile menu, one switcher — consistent across vertical / custom apps.
3) SSO bridge. User logs into the workspace once; platform JWT propagates to every vertical and custom app the user opens. No re-login.
4) Global search. Federated search across all apps the user has access to (via sdk-search + sdk-policy).
5) Cross-app workflows. Approvals, notifications, and inboxes aggregate from every app into one place.
6) Personalization & agents. The Engagement Agent + Conversation Agent live here — a single AI conversational surface that has context across the tenant's apps.
7) App switcher. Persona switcher when the user holds multiple personas (e.g., a doctor at Hospital A AND a patient at Hospital B sees both views).
Composition model
Module Federation (Webpack 5 / Vite Module Federation) for ProjexCloud-owned verticals — each vertical app exposes a remote entry; the workspace composes them as micro-frontends sharing React, design-system, identity context. Lazy-loaded per user permissions.

iframes for tenant custom apps — safer interop (different React versions, different domains, different security postures). Custom app authenticates via OAuth handshake against sdk-identity; communicates with workspace shell via postMessage protocol the platform defines.
Auth
Platform OIDC with full six-layer JWT. The workspace's IdentityContext propagates to every embedded app (Module Federation: shared context; iframes: via postMessage).
Phase
MVP shell in P3 (just shows static cards for subscribed apps); Module Federation host in P4; cross-app workflows + global search in P5; agent surface in P6A.

11.2 · How a custom app shows up here

  1. Tenant developer builds their custom app (separate repo, outside our orgs).
  2. Tenant admin registers the app in the Tenant Admin Portal → Custom Apps: provides a manifest (name, icon, URL, OAuth client_id, required scopes, permissions matrix).
  3. Platform validates the manifest (sdk-tenant-lifecycle), provisions an OAuth client for the app, registers it in the tenant's workspace config.
  4. Next time a tenant employee opens the workspace, the custom app appears alongside verticals in the app switcher.
  5. Click → workspace opens the custom app in an iframe; postMessage handshake establishes JWT context; custom app makes API calls (gated/metered like any other SDK consumer).

Tenant Custom App custom-<slug>.<tenant>.projexcloud.com OR customer's own domain

Hosting

Design system: @projexlight/design-system so custom apps look native to the workspace.
Not exposed: sdk-vault (server only) · sdk-secrets · sdk-pool-router (internal) · sdk-audit (server, customer-read only) · sdk-meter (server, gate only) · sdk-billing (server) · sdk-tenant-lifecycle (server) · sdk-data-rights (server).

12.2 · The five guarantees we make to tenant developers

G1
Same SDK surface as our own teams
Custom apps use the exact same @projexlight/sdk-* packages our verticals use. Same documentation, same support cadence, same versioning. No "lesser SDK for customers."
G2
Same auth + RLS guarantees
Custom app code cannot bypass tenant isolation, ABAC, ReBAC, or consent. The platform enforces these at the SDK gate, not in customer code.
G3
First-class billing & metering
Custom apps' usage shows in the same billing surface as verticals. Customers see per-custom-app breakdown in their bill (the showback dimensions include the app_id of the custom app).
G4
First-class workspace integration
A registered custom app appears alongside verticals; users SSO into it; cross-app workflows (approvals, notifications, AI conversation) include the custom app.
G5
Source code stays the customer's
ProjexCloud has zero access to customer code. Customer can leave any time; their app data is theirs; their app source is theirs.
Caveat
What customers do NOT get
No access to sdk-vault, sdk-meter (gate side), sdk-tenant-lifecycle (operator side), sdk-audit (write side), sdk-data-rights (operator side), or any cross-tenant scope. These are platform-operator-only.

13 · Registry & Publishing

13.1 · One private npm registry, one source of truth

  • Registry: private npm registry hosted at npm.projexcloud.com (Verdaccio, GitHub Packages, or Cloudsmith — operational choice).
  • Scope: @projexlight/ — all packages published under this scope.
  • Auth tokens:
    • Platform CI publishes (write).
    • Vertical repos read with full-scope tokens issued to vertical teams.
    • Tenant developers read with per-tenant tokens issued via Tenant Admin → API Keys; tokens are limited to client-side SDK packages only (registry enforces via custom resolver).
  • Versioning: semver via changesets. Breaking changes ship as new major version + 6-month deprecation of previous.
  • Release cadence: weekly for non-breaking; major versions on a published roadmap.

14.1 · Turbo pipelines

14.2 · Per-PR CI matrix

  1. Workspace install (pnpm with content-addressed cache)
  2. Type-check every changed package + downstream consumers
  3. Lint — including the OC-1..OC-10 custom rules from tools/lint-rules
  4. Contract diff — fails if a published package's public types have breaking changes without a major-version changeset
  5. Test — unit + integration + contract
  6. Pool-placement-matrix freshness check — fails if a new SDK doesn't appear in Architecture §8A
  7. Cross-tenant prompt-leakage test (for any PR touching sdk-agent-runtime or any tool used by agents)
  8. Doctrine compliance — Opinionated Constraints checked against the PR diff

14.3 · Release pipeline

  • Merge to main triggers changeset processing.
  • Changesets bumps versions and writes CHANGELOG.md per package.
  • Tagged release publishes all bumped packages to registry.
  • Services rebuild and roll via ArgoCD / Flux to staging → prod.
  • Each vertical's CI listens for registry publishes; opens PRs in their repos to bump @projexlight/* versions.

14.4 · Migrations

  • Each SDK's db/migrations/ is versioned with timestamp prefixes.
  • tools/migration-runner orchestrates per-pool migrations on a controlled rollout (one pool → 10 pools → 100% in a region → next region).
  • Migrations are forward-only in production; rollback is via a new migration (never reverting). Down-migrations exist only for dev/staging.
  • Phase exit gates require all required migrations to be deployed across all production pools before the next phase's SDKs can start coding.
